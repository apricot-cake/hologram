# サブエージェントの共通ルール

**このスキルは「毎回同じことを言われる部分」の正本**。呼び出し側のブリーフには**その件に固有の設計だけ**が書かれているので、ここに書かれた作法は**ブリーフに書いていなくても適用される**。⚠️**ブリーフとここが食い違ったら、ブリーフが優先**（呼び出し側はこの件の事情を知っている）。

## 1. 隔離＝最初の編集の前に専用 worktree

**最初の編集の前に専用 worktree を作り、以後すべての編集をその中で行う。本体ツリー（`C:\Users\apricot\local\dev\hologram`）は読むだけ。**

- ⚠️**「調査のための一時的な編集」「実験して元に戻すつもりの編集」も含めて全部**。2026-07-31、CSP を本体ツリーで一時的に書き換えて実験したエージェントが停止された。**一時的かどうかは免除の理由にならない**＝並行して複数のセッションが走っており、その間に誰かがビルドすると混ざる。
- **現在地を思い込まない**＝`git rev-parse --show-toplevel` と `git worktree list` で、いまいる場所が登録済みの自分の worktree だと確認する。
- ⚠️**`EnterWorktree` はサブエージェントからは呼べない**（cwd override があるため）。自分で `git worktree add` する。
- ⚠️**`Edit`/`Write` ツールは自分の作業ツリー外への書き込みを拒否する**が、**`Bash` はこのガードの対象外**＝`cd` して直接書けてしまう。**ガードが無い経路でも規則は同じ**。

## 2. 壊してはいけない共有資源

- ⚠️**本体ツリーで `npm run build --workspace=app` / `npm run build:ext` を走らせない。** 本体の `app/out` と `extension/.output/chrome-mv3` は**ユーザーが日常使いしているアプリと拡張の実体**。ビルドは worktree の中で。
- ⚠️**実ライブラリを壊さない。** 書き込みを伴う検証は `HOLOGRAM_CONFIG_DIR` でサンドボックス化する（`scripts/sandbox-app.cts`）。**設定画面の「危険な操作」セクションのボタンを押さない。**
- ⚠️**他のセッションの worktree を消さない**（`git worktree list` に出るもののうち、自分が作ったもの以外）。
- ⚠️**共有スクラッチパッドのファイルを消さない。** 2026-07-31、別セッションのファイルを自分のものと思い込んで削除する事故があった（復元不可）。**自分のファイルには固有名を付ける。**
- ⚠️**`chrome://` の内部ページは触らない**（ユーザーに依頼する領分）。**ユーザーの日常 Chrome のフォーカスを奪わない**＝背面タブのまま CDP で読む／JS を走らせるのが既定。

## 3. 着手前の判定

- **Issue 本文とコメントを全文読む**（`gh issue view <番号> --comments`）＝**設計仕様の家は Issue**。呼び出し側のブリーフより Issue の記述が優先（ブリーフが明示的に上書きしている点を除く）。
- **設計が確定していない**（受け入れ条件が無い・未決が残っている）と分かったら、**実装に入らず設計を先に確定させる**（Issue にコメントで記録）。⚠️その中で**本当にユーザーの判断が要る点（採否・優先度・好み）**に当たったら、**そこは決めずに報告**する（サブエージェントはユーザーに聞けない）。
- ⚠️**新しいライブラリの採用や操作モデルの変更が前提になるなら、実装前に止めて報告**する。**自前実装へ安易に倒さない**＝既存のライブラリ・ツールを先に検討し、候補の比較を添えて報告する。**「依存ツリーに在る」は採用根拠にならない。**
- **判断材料には「標準はどうか」を付ける**＝そのスタックの実プロダクトが実際どうしているかを**一次ソースで確認**して書く。⚠️**確認できなければ「確認できず」**、一意な標準が存在しえない領域（配色・トーン等）は「標準なし」と明記。**憶測の「一般的には」を書かない。** ⚠️**UIアンカー7種は質感のリファレンスであって「何が標準か」の権威ではない**＝標準を調べる時はその外も広く見る。
- ⚠️**引用する Issue 番号は、引用する前に開いてタイトルを見る**（`gh issue view <N> --json number,title,state`）。2026-07-31、記録から借りた番号が2件とも無関係な別件を指していた。**番号は具体的なので、書いてあると裏を取った証拠のように見える。**

## 4. 反映と検証

- ⚠️**main / preload / renderer / native-host を直したら `npm run build --workspace=app`**（native-host のブリッジ本体なら `npm run build:native-host-bridge --workspace=app` も）。**走らせないと古いバンドルのまま動き、直っていないものを検証してしまう。**
- **`npm run check` を通す。** ⚠️ただし**変更の種類によっては check が何も見ないことがある**（`.md`/`.txt` は Biome の対象外・typecheck も Vitest も見ない）。**緑を根拠にする前に、その変更を check が実際に踏むかを確かめる。**
- **UI を変えたら見た目パスは必須**（skill `verify-with-cdp` / `run-hologram`）。ライト/ダーク両方。
- 拡張を触ったなら skill `verify-extension`。テストを worktree で回すなら skill `test-in-worktree`。

## 5. 出口＝ここまでやって完了

1. PR 作成（着地させる Issue に `Closes #N`。⚠️**ユーザーの確認が残るなら `Closes` を使わない**＝マージで自動クローズされ、実態と食い違う）
2. **自己マージ**（許可済み・**CI の完了は待たなくてよい**）
3. 本体ツリーへ戻る（`git checkout main` ＋ `git pull --ff-only`）
4. **worktree とブランチ（ローカル・リモートとも）を掃除**
5. **本体ツリーがクリーンであることを `git status --porcelain` で確認**

⚠️**ユーザーの操作でしか確認できない項目が1つでも残るなら、PR がマージ済みでも「完了」と呼ばない**＝Issue は閉じず、自セッション内でユーザーへ直接聞く。

## 6. 報告

- **ユーザーへの説明・質問・報告はすべて日本語で。** コード内コメントとコミットメッセージは英語が正。
- ⚠️**詳細の家は PR コメント（設計の話なら Issue）。呼び出し元へ返す本文は5行以内。** 返してよいのは①結論②検証が緑か赤か③残している作業④拾った別件、の4点だけで、**変更の理由・検討した代案・検証の手順と生ログ・差分の全文・ブリーフの復唱・自分が書いた PR 本文の貼り直し**は返さず PR 側へ書く。
  - **理由＝呼び出し元のコンテキストは毎ターン再送される。** 長い着地報告は1本あたり1〜2k tokens で、しかも Issue/PR と同じ内容の二重持ち＝それが着地のたびに積まれて以後ずっと再送され続ける（2026-07-31 に実測で問題化＝30件超が積まれた）。**PR に書けば呼び出し元の外に置けて、必要な時だけ読み直せる。**
- ⚠️**サブワーカーを出すなら同期で回す**（`Agent` の `run_in_background: false`）。**背景で出すと完了通知が呼び出し元にも別便で届く**＝自分の報告と二重に積まれる（2026-07-31、#59 でサブワーカーの完了通知が親へ8通落ちた）。出す前に「本当に分ける必要があるか」を先に疑う。
- ⚠️**タスクチップ（`spawn_task`）を作らない。** 別件を見つけたら **Issue を起票するところまでは行ってよい**が、チップの発行は進捗管理セッションに一本化されている（並列可能性を管理しているのがそこだけのため）。見つけたものは**報告本文に1行で書く**（詳細は起票した Issue が持つ）。
- **報告には「やった結果」だけでなく「確かめられなかったこと」も書く**＝未確認を確認済みと同じ口調で並べない。

## 7. 並行作業

複数のセッションが同時に走っている前提で動く。

- ⚠️**Issue への書き込みは git と違って衝突検知が無い**（後勝ちで黙って消える）。本文・タイトル・Status を書き換える前に skill `issue-concurrent-writes`。様式は skill `issue-style`。
- 着手前に `list_sessions` でログまで読み、**同じ Issue への二重着手**を避ける。
- ⚠️**GraphQL の枠は共有**＝`gh` の issue/project 系はノード数で課金され、枯らすと `gh issue create` まで落ちる。**確認のためにボード全件・全 Issue を引き直さない。** 全数照合は REST 1回（`gh api --paginate "repos/apricot-cake/hologram/issues?state=all&per_page=100"`）でローカル grep。
