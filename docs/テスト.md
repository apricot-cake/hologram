# テスト

テストは、速く確認できる単体・統合テストから、実際のアプリとブラウザを動かすテストまで段階的に用意しています。変更に近い層から実行し、保存経路や画面操作に関わる変更では上位の層も実行してください。

## まず実行するコマンド

| 目的 | コマンド |
| --- | --- |
| 静的解析、型検査、単体・統合テスト | `npm run check` |
| 単体・統合テストのみ | `npm test` |
| 拡張機能のソースと Chrome テスト用バンドル | `npm run check:ext` |
| Chrome のリリース成果物 | `npm run release:ext:verify` |
| 型検査のみ | `npm run typecheck` |
| アプリ、ネイティブホスト、拡張機能の結合テスト | `npm run test:integration` |
| 実ポインタ・実キー操作による画面 E2E | `npm run test:e2e:all` |
| 通常の画面フロー E2E のみ | `npm run test:e2e:app` |
| ビジュアル基準画像を更新する | `npm run test:e2e:visual:update` |
| 拡張機能のオフライン E2E | `npm run test:e2e:ext` |

依存関係がないワークツリーでは、先に `npm run setup` を実行してください。

## テストの使い分け

### 型検査

`npm run typecheck` は拡張機能の型定義を `wxt prepare` で生成し、ルートの `tsconfig.json` から Project References をたどって `tsc -b` で7領域を検査します。アプリ内では `app/tsconfig.json` がメインプロセスとレンダラーをまとめます。各領域の実行環境に合わせた設定と検査対象は、それぞれの tsconfig で管理します。

JavaScriptや型宣言は出力せず、増分検査の情報だけを `node_modules/.cache/typescript/` に保存します。このディレクトリは既存の `node_modules/` の除外に含まれ、Gitには入りません。

`npm run typecheck -- --verbose` で領域ごとの検査・省略理由を表示し、`npm run typecheck -- --force` で全領域を再検査できます。型エラーにはファイル名・行番号が表示され、終了コードは非ゼロになります。

### `npm test`

Vitest による単体・統合テストです。純粋な変換、データベースの振る舞い、IPC の契約、レンダラープロセスの状態管理などを確認します。ビルド済み拡張機能を直接読むテストは含みません。ロジックを変更した場合は必ず実行してください。

### `npm run check:ext`

通常の検証に加え、`extension/.output/chrome-mv3-test/` に Chrome のテスト専用バンドルを作り、生成されたマニフェスト、注入用スクリプト、ページ内 UI を検査します。拡張機能のソース、マニフェスト、またはバンドル方法を変更した場合に実行してください。ほかの出力先は変更しません。

### `npm run test:integration`

Electron アプリ、ネイティブメッセージングホスト、拡張機能の境界を通すテストを実行します。各テストは一時ディレクトリと専用の設定を使うため、通常は実ライブラリや起動中のアプリに影響しません。

アプリは事前に `npm run app:build` でビルドしてください。テスト用拡張機能は、このコマンドの実行前に自動でビルドします。

一部だけ実行する場合は、Playwright の `--grep` でテスト名を指定できます。

```powershell
npm run test:integration -- --grep "tabs|extension-orphan"
```

並列実行で不安定になる場合だけ、次のように並列数を下げます。

```powershell
npm run test:integration -- --workers=1
```

### `npm run test:e2e:all`

Playwright の全プロジェクトを実行します。画面フローは `flow`、ビジュアル検証は `visual`、隔離プロセスは `harness`、拡張機能は `extension` に分けています。実際のポインタとキー入力で、クリックできない要素、重なり、レイアウト、キーボード操作を確認します。起動前にアプリをビルドする必要があります。

```powershell
npm run app:build
npm run ext:build:test
npm run test:e2e:all
```

基準画像の更新は意図した見た目の変更を確認してから行ってください。環境による差を直す目的で無条件に更新しません。詳細は `e2e/README.md` を参照してください。

### 隔離プロセスを使う理由

`harness` の各ケースは、起動前の設定、再起動、標準出力、終了コードを検証します。ケース内の `process.exit` や環境変数がテストランナーに影響しないよう、Node の子プロセスで実行します。ケースの検出・並列実行・タイムアウト・シャード分割・ログの添付は Playwright が担当します。失敗時の全ログはテスト結果の `harness.log` を確認してください。

### 拡張機能の E2E

`npm run test:e2e:ext` は、Chrome のテスト専用バンドルを作ってから Playwright の `extension` プロジェクトを実行します。テストは使い捨ての Chromium と Chrome のテスト専用バンドルを使います。保存のタイムアウト、重複保存、ページ上の UI、拡張機能の更新後の状態を確認するときに実行してください。

スクリプトの一覧と実行内容は、リポジトリ直下の `package.json` を参照してください。

### 手動の診断ツール

`scripts/self-test.cts` はインストールと Native Messaging の接続、`scripts/test-metadata.cts` は実際の SNS の応答、`scripts/test-watch-verify.cts` は保存済みライブラリを調べる CLI です。利用者の環境や外部データを対象にするため、自動テストのスイートには入れません。開発・運用の診断ツールとして `scripts/` に置きます。

## 配置と実行方式

2026-09-09 に、単体テストは実装の隣、結合テストは `tests/integration/`、アプリやブラウザを動かす検証は `e2e/` に分けると決めました。開発・配備用の処理は `scripts/` に置きます。フィクスチャは `tests/fixtures/`、ブラウザ起動など E2E 専用の補助コードは `e2e/lib/` に置きます。

[Vitest の配置ガイド](https://main.vitest.dev/guide/learn/testing-in-practice#file-layout)は隣接配置と専用ディレクトリの両方を認めています。単体テストは実装との対応を探しやすくし、複数領域にまたがるテストは一つの実装に所属させないため、この分け方を採用しました。

実行方式は Vitest と Playwright に揃えます。[Playwright の並列実行](https://playwright.dev/docs/test-parallel)と[シャード分割](https://playwright.dev/docs/test-sharding)を使うため、独自の実行プールは持ちません。

## 新しいテストを追加する

- 単体テストは対象ファイルの隣に `*.test.ts` として置きます。開発ツールの単体テストも、そのツールの隣に置きます。
- DB・保存・取り込みなど複数の処理をつなぐテストは `tests/integration/`、共有の補助コードは `tests/helpers/` に置きます。
- 起動前の設定や終了コードなど、プロセス隔離が必要な検証は `e2e/harness/cases/test-app-*.cts` として追加します。画面上で完結する検証は Playwright の `*.spec.ts` として追加します。
- 実際の画面操作や視覚的な結果は `e2e/flows/` または `e2e/visual/` に追加します。
- 拡張機能のブラウザ上の挙動は `e2e/extension/*.spec.ts` に追加します。

テストは、実データ、固定ポート、共有の設定ディレクトリ、既存のブラウザプロファイルに依存しないようにしてください。必要な状態は各テストで作成し、終了時に片付けます。

## 手動で投稿を確認する

自動テストで確認できない投稿は、開発用 Chrome とサンドボックスライブラリを使って確認してください。通常タブの保存先を変えずに検証用タブを開く手順は、[CONTRIBUTING.md](CONTRIBUTING.md) の「拡張機能を開発する」を参照してください。

実サービス上の投稿を試す場合は、公開範囲、ログイン状態、投稿内容が結果に影響することを記録してください。個人情報や認証情報をテストデータ、ログ、スクリーンショットに残さないでください。
