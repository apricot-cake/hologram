# クエリビルダー再設計 — ゾーン廃止＋属性ごとのファセット・トグル

設計確定: Opus 4.8。**最新＝末尾の「改訂③」＝バー上でドラッグして括弧で組むインライン・
ビルダー（2026-06-19 実装済み）**。ファセット版（本文）と改訂②（条件ツリー＋入れ子パネル）は
その前段で、改訂③が**パネルUI・自動型まとめ・per-type 演算子 select を置換**した（ツリー・
モデルと再帰評価は流用）。本文・改訂②は経緯として残す（現行UIではない）。
UI 変更なので実装時は [DESIGN.md](../DESIGN.md) に従うこと。

## 背景（現状の問題）

現状のビルダーは「かつ箱」「または箱」の2ゾーン固定構造で、式の形が
`(かつ箱を全部AND) ⟨tagJoin⟩ (または箱を全部OR)` に固定されている
（[`renderQueryChips` at app/renderer/viewer.js:579](../app/renderer/viewer.js:579)）。

- **演算子が3か所に分散**している:
  1. 箱の見出しの「かつ/または」
  2. ピル間の `.qc-op`（[viewer.js:611](../app/renderer/viewer.js:611)）＝**飾りで非interactive**
  3. 箱の間の `qcJoinSel` プルダウン（`tagJoin`）＝唯一編集できる接続演算子
- ピルの `mode`（`'and'`/`'or'`）が**どちらの箱に入るか＝位置で演算子を表す**ため、
  AND ⇄ OR の変更にはピルの**ドラッグ移動が必須**（[dragstart/dragover/drop at viewer.js:765-](../app/renderer/viewer.js:765)）。
- 一番「押せそう」に見える 2 の `.qc-op` が押せない＝直感と実装のズレ。
- ユーザーが自然だと感じる導線（ピル間の演算子をプルダウンで変える）を許すと
  `A かつ B または C` のような混在式になり、2ゾーンモデルでは表現不能。両者は両立しない。

## 採用モデル — ファセット（Linear / Notion / Amazon 系の絞り込み）

- **ピルは属性（`type`）ごとに自動でまとまる**。位置に演算子の意味を持たせない
  → **ドラッグ移動が消える**（タグを動かさない）。
- **属性どうしは常に AND**（最も直感的な既定＝「全部満たす投稿を出す」）。
  属性間の「かつ」は**固定表示・読むだけ**（編集不可）。これにより混在式が原理的に生まれない。
- **属性 “内” にだけ、その場のトグル**「いずれか(OR) / すべて(AND) / 除外(NOT)」を置く。
  - 例: タグ群 `[抱きしめ] [口]` の脇のトグルを「すべて」にする＝AND。タグは動かさない。
  - **値が2つ以上のときだけトグルを出す**（1値では OR/AND が同義）。
- **除外(NOT) は新機能だが直感コスト0で同居**できる（`is / is not` の語彙は周知）。
  `抱きしめ かつ 口でない` が一発で組める。表現力だけ上がる無料の拡張なので入れる。

## データモデルの変更

- 現状: `activeFilters: {type, value, mode}[]` ＋ グローバルな `tagJoin`。
  - `mode`（zone 振り分け）と `tagJoin`（箱間の接続）は**廃止**。
- 新: 演算子を**属性（type）単位**で持つ。例 `typeOps: { tag: 'and'|'or'|'not', ... }`
  （既定 `'or'`＝従来「クリックでまず または箱に入る」と同じ既定）。
  ピル自体は `{type, value}` に簡素化。
- 評価: 各 type 内をその type の演算子で畳み、**type 間は AND** で結合。
  - `qbHelp6` の「単一値 type（platform 等）は かつ箱でも自動的にどれか1つ(OR)」という
    既存のファセット的挙動は、この新モデルの自然な特例として吸収される。

## 廃止 / 書き換え

- 廃止: かつ箱・または箱、`qcJoinSel`、`.qc-op` の飾り、ピルのドラッグ移動
  （`dragstart`/`dragover`/`drop` ハンドラ）、`tagJoin`、ピルの `mode`。
- i18n（[app/renderer/i18n.js](../app/renderer/i18n.js)）: `qcDropHere`/`qcDropMove` 撤去。
  `qcJoinAnd`/`qcJoinOr` はトグルのラベル（いずれか/すべて）に転用 or 新キー。
  除外用の新キー追加。`qbHelp1`〜`qbHelp6` をファセット説明に全面書き換え。

> 注: 下の「スコープ外」「拡張のハシゴ」「未決」は、ファセット版を出した時点の整理。
> 「改訂 2026-06-18②」で**完全表現へ進む**ことになり、これらは吸収・解決済み（各節末に注記）。

## スコープ外（→ 改訂②で解決）

- **跨ぎ OR**（`プラットフォーム=X または タグ=口`）はファセット単体では表現できない。
  - ※ **改訂②の条件ツリーで表現可能になった**（ルートを OR にできる）。

## 拡張のハシゴ（→ 改訂②で実行）

- ファセットのバーは **完全な条件ツリーの平坦な特殊ケース**（ルートAND × 属性ごとのグループ）。
- 表現力×直感さのフロンティア上で、ファセットは**膝**。完全表現（ブール完全）はさらに右で
  直感さの急坂の先 → だが**段階的開示**なら1点で選ばずフロンティアを*またげる*（改訂②）。

## 未決（→ 改訂②で解消）

- 「跨ぎ OR の頻度」を測る、という未決は**不要**になった。完全表現なので頻度に関係なく
  表現でき、複雑さは*使ったときだけ*出る（段階的開示）。

  演算子 select。評価＝[viewer.js:1938](../app/renderer/viewer.js:1938) で型ごとに畳み型間 AND。
  `activeFilters`（`mode` 廃止）＋ `typeOps`。i18n / CSS / DESIGN.md 追従済み。
  検証: `scripts/_verify-tagmix.js`（or/and/not）・`test-app-postfilter.js` PASS。

## 改訂 2026-06-18②: 完全表現へ — 段階的開示の条件ツリー（確定・段階1着手）

ファセット版実装後、ユーザー判断「表現力を一切落としたくない」＝フロンティアの右端
（ブール完全）を選ぶ。ただし日常クエリの直感性は捨てず **段階的開示**でフロンティアを
またぐ（前例: Notion の filter group / Airtable / Linear）。**ファセットのバーは廃止せず、
この木の平坦な特殊ケース＝デフォルト表示として存続する。**

### データモデル ＝ 条件ツリー（ブール完全）

- **葉** `{ kind:'cond', type, value, neg?, …(date/eng のパラメータ) }` — 既存 `predOf` を
  そのまま使い、`neg` で否定。
- **グループ** `{ kind:'group', op:'and'|'or', neg?, children:[…] }` — 子（葉/グループ）を
  AND/OR で畳み、**入れ子可**。ルートはグループ（既定 `op:'and'`）。
- 評価は再帰1本（`evalNode`）: cond → `predOf` を `neg` で XOR ／ group → `some`/`every` を `neg` で XOR。

### ファセット ＝ この木の特殊ケース（捨てない）

- ルート `group(and)` ＋ 属性ごとに子 `group`: `いずれか`→`op:or`／`すべて`→`op:and`／
  `除外`→`op:or, neg:true`（＝どれも無い）。日付・反応・WS はルート直下の葉。
- 既存の `activeFilters`＋`typeOps` から `facetTree()` でこの木を導出して評価する
  （`typeOps` は「1階建てグループの sugar」）。これで**跨ぎOR・入れ子・型内 AND/OR 混在・
  単値否定**が、すべて木の一般形で表現でき＝**表現力の損失ゼロ**。

### UX ＝ 段階的開示

- **A. 編集パネル ＝ バー下に開くガラスのポップ**（浮遊面＝ガラス／フライアウトは行の下右＝
  DESIGN.md 準拠。前例 Notion の filter 編集ポップ）。
- **B. バー**: 木が「ルートAND × 属性ごとの単型グループ」の平坦形のとき＝**今のファセット
  バーのままインライン編集**。それを外れた瞬間（ルートOR・入れ子・型混在・葉単位の否定）だけ
  バーは**括弧つきの読み取り要約＋「編集」**へ。構造編集はパネルに寄せる（入れ子のピル単位
  インライン編集は階層が曖昧なので持たせない）。
- **C. パネル**: Notion 式の入れ子グループ・エディタ。各グループ見出しに
  `すべて満たす/いずれか/除外 ▾`、行ごとに 否定/削除、`＋条件`/`＋グループ`。

### 段階（各段で動く・回帰最小）— **1〜3 実装・実機反映済み（2026-06-18）**

1. ✅ **ツリーのモデル＋再帰評価＋ファセット導出**（`facetTree()`＋`evalNode`＋`currentTree()`。
   UI不変・挙動完全一致）。
2. ✅ **入れ子エディタ（ガラスパネル `.qb-panel`）** ＋ 実 `queryTree` 状態（複雑時の真実源・
   `facetTree()` を上書き）＋ 永続化（タブ状態 `tree`）。値追加＝`＋条件`→種類チューザー→
   既存フライアウト(qfPop)の pick モード。`シンプルに戻す`＝平坦な木なら faceted へ降格。
3. ✅ **バーの複雑時要約（括弧つき・読み取り）＋ `編集`／faceted 時の `詳細` 入口**。
   詳細モード中はサイドバーのフライアウト値はルートグループへ追加。

検証: `scripts/_verify-tree.js`（跨ぎOR=3／AND=1／要約／編集）・`_verify-tagmix.js`
（ファセット回帰）・`test-app-postfilter.js` いずれも PASS。

未磨き（既知・任意の追い込み）: ① サイドバーのピン/フォルダ“チップ”は詳細モードでまだ
faceted 経路（行→フライアウトはルート追加で動く）。② フライアウトのチェックはルート直下

## 改訂 2026-06-19③: ドラッグ式インライン・ビルダー（実装済み 2026-06-19）

改訂②の入れ子パネルを実機で詰める中で、ユーザーが紙で再設計（手書きメモ8枚）。方針転換:
**パネルを廃し、バー上で直接ドラッグして括弧で組む**インライン・ビルダーにする。**改訂②の
UI（グループ箱パネル `.qb-panel` ＋ 詳細/編集入口 ＋ qfPop pick モード ＋ 自動型まとめ）は
これに置き換えた。** ただし**段階1のツリー・モデル＋再帰評価（`evalNode`/`currentTree`/
タブ状態 `tree`）は流用**（新モデルの編集結果も同じブール木を作るため）。

> **実装メモ（2026-06-19）**: `queryTree` を**単一の真実源**にした（常にルートグループ・
> 既定 `op:'and'`）。`activeFilters` はツリーの葉から導出する**シャドウ**で、サイドバーの
> 強調/件数バッジ/タブ名のみが参照（`syncShadow()`）。`typeOps`/`facetTree`/`.qb-panel`/
> qfPop pick モードは撤去。バーは `renderQueryChips()` がツリーを直接描画（`.qb-pill`＝
> 条件・`.qb-grp`＋`.qb-paren`＝グループ・`.qb-op`＝AND/OR トグル・`.qb-del-btn`＝ホバー✕削除・
> 否定/削除は右クリックメニュー `.qb-menu`＝否定中は先頭に ≠ 表示）。
> ドラッグは HTML5 DnD で **e.target ベース**に当たり判定（ピル＝対グループ化／括弧・演算子＝
> 丸ごと移動・枠ドロップ＝ネスト／グループ内＝メンバー追加／余白＝トップ階層へ戻す）。
> 1メンバー化したグループは `cleanupTree()` が自動で括弧解除。サイドバーの各入口
> （フライアウト/チップ/日付・反応ポップ/フォルダ/WS/投稿者）は `addFilter()` でトップ階層へ
> 追加に統一。**連結語クリックでトグル**＋**忠実版ドロップ判定**（ユーザー選択 2026-06-19）。
> 旧タブ状態（`f`+`ops`・`tree` 無し）は `facetTreeFrom()` で移行。
> 検証: `scripts/_verify-tagmix.js`（トップ階層AND既定・連結語トグル・≠否定）・
> `_verify-tree.js`（ドラッグでの跨ぎOR・パネル不在）・`test-app-postfilter.js` いずれも PASS。

### スコープ
- **クエリビルダーの中だけ**の再設計。サイドバー（種類別の入口＝条件のピッカー）は不変。

### 基本構造
- **自動の型まとめを廃止**。条件は種類に関係なくフラットに並ぶ（タグも日付も同列の「条件」）。
  ＝改訂②までの「属性ごと自動グループ＋per-type 演算子 select（いずれか/すべて/除外）」をやめる。
- グループは**括弧 ( ) で literal に表示**（箱で囲わない）。
- グループの演算子は**1つ（かつ/または）・プルダウンで一括切替**（メンバー全員同じ）。
  混ぜたいときは必ずグループ化＝それが括弧の存在理由。

### 作成・編集 — ドラッグが主役（万能ジェスチャー）
- **ピル→別ピル** に重ねる: その場で `(c1 op c2)` グループ（**兄弟グループも作れる**）。
- **ピル→グループの中**: メンバー追加。**ピル→グループの外**: メンバー削除。
  **1メンバーになったら括弧は自動で消える**（＝解除）。
- **グループを枠ごと**（括弧 or 演算子ラベルを掴む）→別の条件/グループに重ねる:
  新しい外側グループで囲う＝**ネスト**。掴む対象で「中身編集／丸ごと」を分ける。
- **「グループ追加」ボタン（バー右）**: 今の式ぜんぶを一発で囲う＝ネストのショートカット。
  **押すたび深くなる・無制限**（一部だけ選んで囲うのは無し＝常に全体）。
- **削除＝ホバーで出る ✕**（ピル右端・枠の内側）。プレーンなピルの**左クリック本体は何もしない**
  （＝ドラッグのつかみどころ。日付・反応ピルだけ左クリックで編集ポップ）。新しい条件はサイドバーの
  種類別フライアウトから選んで**トップ階層に載る**。

### 演算子の既定
- トップ階層＝**かつ**。
- **ドラッグで作った群＝親（周囲）の逆**（混ぜたくてグループ化するので内側は外側と違うはず。
  「かつ」の並びでドラッグ→`(○ または ○)`／逆も同様）。後からプルダウンで変更可。

### 否定（NOT）・削除 — 右クリックメニュー（2026-06-19②: ホバー≠から変更）
- 旧ホバー≠は**初見で意味が分からず**、枠の外に飛び出して隣や上の行に被って**邪魔**だった
  （ユーザー指摘）。否定は低頻度・上級操作なので、カードと同じく**右クリックのメニュー**
  （`.fold-menu` 様式・DESIGN.md の「右クリック＝アクションの目次」）に畳む。削除は誰でも分かる
  **ホバー✕**に独立させる（左クリック本体は何もしない＝ドラッグ優先）。
- **要素**: 右クリック→「除外（〜でない）」。否定中はピル先頭に淡い ≠ ＋ラベル取り消し線。
- **グループ**: 括弧/演算子/グループ本体を右クリック→「グループを否定（≠）」。否定中は `≠(…)`。
- メニューは要素・グループとも「否定トグル＋削除（赤 `fm-danger`）」。**AND/OR とは独立**
  （連結語クリック＝中身の結合、否定＝そのまとまりを反転）。1グループで4通り:
  `(C または D)` / `(C かつ D)` / `≠(C または D)`(=どちらも無い) / `≠(C かつ D)`(=両方は揃わない)。
- 表示は要素・グループとも **≠ 前置**で統一（「でない」より短く一貫）。

### 表現力
- ブール完全を維持（兄弟＋ネスト＋AND/OR＋否定）。例: `(A または B) かつ (C または D) かつ E でない`。

### 実装メモ
- **流用**: `evalNode`（葉＋AND/OR/neg グループ・再帰）・`currentTree`・タブ状態 `tree` 永続化。
- **撤去/置換**: `.qb-panel`（入れ子パネル）・種類チューザー・qfPop pick モード・バーの
  「詳細/編集」入口・`facetTree`/`typeOps`（自動型まとめ）・ファセット per-type 演算子 select。
  新ビルダーは**バー上で直接**: 括弧描画＋ドラッグ(DnD)＋ホバー✕削除＋右クリック否定メニュー＋
  グループ追加ボタン＋グループごとの演算子プルダウン。
- DnD のドロップ判定（中 vs 枠）の当たり判定、キーボード代替、`prefers-reduced-motion`、
  1要素グループの自動解除タイミングは実装時に詰める。
