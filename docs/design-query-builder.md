# クエリビルダー再設計 — ゾーン廃止＋属性ごとのファセット・トグル

設計確定: Opus 4.8（2026-06-18・ユーザー承認済み「これでいい」）。実装は未着手。
UI 変更なので実装時は [DESIGN.md](../DESIGN.md) に従うこと。

## 背景（現状の問題）

現状のビルダーは「かつ箱」「または箱」の2ゾーン固定構造で、式の形が
`(かつ箱を全部AND) ⟨tagJoin⟩ (または箱を全部OR)` に固定されている
（[`renderQueryChips` at app/renderer/viewer.js:579](../app/renderer/viewer.js:579)）。

- **演算子が3か所に分散**している:
  1. 箱の見出しの「かつ/または」
  2. ピル間の `.qc-op`（[viewer.js:611](../app/renderer/viewer.js:611)）＝**飾りで非interactive**
  3. 箱の間の `qcJoinSel` プルダウン（`tagJoin`）＝唯一編集できる接続演算子
- ピルの `mode`（`'and'`/`'or'`）が**どちらの箱に入るか＝位置で演算子を表す**ため、
  AND ⇄ OR の変更にはピルの**ドラッグ移動が必須**（[dragstart/dragover/drop at viewer.js:765-](../app/renderer/viewer.js:765)）。
- 一番「押せそう」に見える 2 の `.qc-op` が押せない＝直感と実装のズレ。
- ユーザーが自然だと感じる導線（ピル間の演算子をプルダウンで変える）を許すと
  `A かつ B または C` のような混在式になり、2ゾーンモデルでは表現不能。両者は両立しない。

## 採用モデル — ファセット（Linear / Notion / Amazon 系の絞り込み）

- **ピルは属性（`type`）ごとに自動でまとまる**。位置に演算子の意味を持たせない
  → **ドラッグ移動が消える**（タグを動かさない）。
- **属性どうしは常に AND**（最も直感的な既定＝「全部満たす投稿を出す」）。
  属性間の「かつ」は**固定表示・読むだけ**（編集不可）。これにより混在式が原理的に生まれない。
- **属性 “内” にだけ、その場のトグル**「いずれか(OR) / すべて(AND) / 除外(NOT)」を置く。
  - 例: タグ群 `[抱きしめ] [口]` の脇のトグルを「すべて」にする＝AND。タグは動かさない。
  - **値が2つ以上のときだけトグルを出す**（1値では OR/AND が同義）。
- **除外(NOT) は新機能だが直感コスト0で同居**できる（`is / is not` の語彙は周知）。
  `抱きしめ かつ 口でない` が一発で組める。表現力だけ上がる無料の拡張なので入れる。

## データモデルの変更

- 現状: `activeFilters: {type, value, mode}[]` ＋ グローバルな `tagJoin`。
  - `mode`（zone 振り分け）と `tagJoin`（箱間の接続）は**廃止**。
- 新: 演算子を**属性（type）単位**で持つ。例 `typeOps: { tag: 'and'|'or'|'not', ... }`
  （既定 `'or'`＝従来「クリックでまず または箱に入る」と同じ既定）。
  ピル自体は `{type, value}` に簡素化。
- 評価: 各 type 内をその type の演算子で畳み、**type 間は AND** で結合。
  - `qbHelp6` の「単一値 type（platform 等）は かつ箱でも自動的にどれか1つ(OR)」という
    既存のファセット的挙動は、この新モデルの自然な特例として吸収される。

## 廃止 / 書き換え

- 廃止: かつ箱・または箱、`qcJoinSel`、`.qc-op` の飾り、ピルのドラッグ移動
  （`dragstart`/`dragover`/`drop` ハンドラ）、`tagJoin`、ピルの `mode`。
- i18n（[app/renderer/i18n.js](../app/renderer/i18n.js)）: `qcDropHere`/`qcDropMove` 撤去。
  `qcJoinAnd`/`qcJoinOr` はトグルのラベル（いずれか/すべて）に転用 or 新キー。
  除外用の新キー追加。`qbHelp1`〜`qbHelp6` をファセット説明に全面書き換え。

## スコープ外（意図的に捨てる）

- **跨ぎ OR**（`プラットフォーム=X または タグ=口`）は表現できない。
  - 理由: ① 個人メディアタガーでの出現頻度が極端に低い ② ちょうど直感さが崖になる領域
    （行や括弧が必須）。現状の 2ゾーンモデルもまともに表現できておらず実害は小さい。

## 拡張のハシゴ（行き止まりではない）

- ファセットのバーは **DNF（AND群のOR）の「1行」と同じ構造**。
- 将来どうしても跨ぎ OR が要るなら「**OR の行を足す**」だけで、設計を壊さず地続きに
  DNF（ブール完全）へ登れる。今は YAGNI で入れない。
- 表現力×直感さのフロンティア上で、ファセット案は**膝（収穫逓減点）**に位置する。
  理論上の頂点（DNF行 / 入れ子＋括弧＝ブール完全）はさらに右だが、直感さの急坂の先。

## 未決（実装前に確認したい実測値）

- ユーザーが「跨ぎ OR」を実際にどれくらい組みたいか。
  - ほぼ無い → 膝で確定（本設計のまま）。
  - 意外と多い → 最初から DNF行（OR行つき）まで前倒しする価値あり。

## 実装の足がかり

- 入口: `renderQueryChips`（[viewer.js:579](../app/renderer/viewer.js:579)）の zone 描画を
  type グルーピング＋per-type トグルへ。`addFilter`（[viewer.js:687](../app/renderer/viewer.js:687)）の
  `mode:'or'` 既定は `typeOps` 既定へ移す。
- 既にこの方向に寄っている箇所: `qbHelp6` のファセット的挙動、サイドバーの
  「絞り込み＝全属性の完全な目次」思想（[docs/design-sidebar-grammar.md](design-sidebar-grammar.md)）。
