# IPC のデータ契約

入力は `app/src/shared/ipc-inputs.ts`、保存データの構造と既定値は `data-schemas.ts` に定義する。型は Zod の `input` / `output` から導く。チャネルの戻り値は `ipc-results.ts` を main と preload の両端で使う。

`activity-ipc.ts` は全チャネルの送信元と引数を検証する。配備済みのアプリ入口、または明示された開発サーバーの最上位フレームだけを受け付ける。入力が不正ならハンドラを実行しない。ログにはチャネルと問題の位置・種類を記録し、ペイロード全体は記録しない。

DB の置換処理も共通スキーマを使う。IPC 以外に ZIP 取り込みからも呼ばれるため、検証に成功してから既存行を置き換える。省略可能な値の既定値と、不正値の読み替えは区別する。不正値を空配列へ変えて保存しない。

## 移行対象

| 対象 | 実装 |
| --- | --- |
| IPC 83応答チャネル・2イベント | 共通入力定義、送信元検証、型付き登録 |
| 環境設定18項目 | キー・値・既定値を共通定義へ移行 |
| フォルダ・グループ・タグ・プロフィール | 保存前の共通検証と型導出 |
| タブ・ナビゲーション | 保存形式と復元処理を共通定義へ移行 |
| ZIP の整理情報 | 統合前に検証。不正な整理情報では DB トランザクションを戻す |
| テスト | 全チャネルの定義漏れ、送信元、不正入力時の保存内容維持、保存・復元を確認 |

## 投稿の取り込み・復旧

投稿の保存形式・既定値と型は `native-host/post-schemas.mts` で共有する。`post-record.mts` は検証後に取得時刻を付け、画像と動画の保存先を整理する。タグ名の NFKC 正規化と重複除去は、文字列配列の検証後に行う。

一覧表示の投稿・プロフィールは `app/src/shared/post-view-schemas.ts` で保存スキーマから導く。DB の読み出し、IPC、レンダラーで同じ型を使う。ゴミ箱やタグの再計算中には存在しない集計値を、表示用の型で区別する。切り抜き範囲とメディアの型も保存スキーマを共有する。

Native Messaging の要求・応答と取得前のメタデータは `native-host/protocol.mts` に定義する。要求が不正ならダウンロードや保存を始めず、既存の失敗応答に項目の位置とエラーの種類を載せる。ペイロードの値は載せない。拡張機能の投稿型と初期値も、この共有定義から導く。

取込キューは `InboxEnvelopeSchema` でエンベロープと投稿を検証する。ハッシュは、既定値を補う前のレコードで照合する。ZIP の投稿と復元フラグは保存前に検証する。不正な投稿を含む ZIP では DB トランザクションを戻す。既にコピーした媒体ファイルは残るため、DB とファイルの操作全体がアトミックになるわけではない。

`restorePostFlags` は `PostFlagsSchema` を使う。ゴミ箱からの復元はファイルを移す前に投稿・フラグ・所属を検証する。投稿とフラグは同じ DB トランザクションで戻す。復元先のフォルダが既に削除されていた場合の所属判定は、構造検証とは別の処理として残る。

DB の JSON 列は保存時と同じスキーマで読む。破損した列やゴミ箱のレコードは警告を記録し、表示できるデータだけを返す。この読み取りで保存内容を書き換えない。新規の取り込みで不正値を欠損へ読み替えることとは区別する。

## 取得元の必須値と欠損

仕様上の欠損は受け付ける。必須値の欠落や、届いた値の型・範囲の不正は保存エラーにする。Zod の検証エラーと不正な JSON は、取得処理の部分保存へフォールバックしない。

`extension/utils/extractor/api-schemas.ts` が取得元の契約を持つ。Bluesky の投稿件数は公式 Lexicon で省略可能だが、本文・作成日時や投稿の識別情報は必須。X の埋め込み用 API と pixiv AJAX の件数は `scripts/canary/snapshots/` の正常応答で確認した契約に基づく。X の `possibly_sensitive` はテキスト・引用・返信のサンプルで欠けるため、省略可能とする。X API v2 の契約を埋め込み用 API の根拠には使わない。

画像一覧、引用、リンクカード、プロフィール、うごイラのコマも、読み取る構造を検証してから組み立てる。不正な要素を配列から除いて保存しない。対応する動画形式の選択、表示用の空文字処理、通信失敗時の既存の取得方針は構造検証と区別する。修正が必要な契約違反は既存のエラー応答・ログに載せ、自動 Issue 作成は追加しない。

フォルダの親子関係、参照先の存在、タグの正規化・衝突、トランザクション、URL と投稿 ID の対応付けは構造検証とは別の処理として残る。
