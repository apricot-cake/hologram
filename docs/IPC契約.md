# IPC のデータ契約

保存済みバッジの投稿リンクは `app/src/shared/post-link.ts` のスキーマで検証する。`hologram://post` は保存済み投稿の表示だけを行い、保存や削除は行わない。個別保存は保存時のメディア URL も照合する。起動前に届いたリンクは、レンダラーの初回読み込み後に `take-post-link` で受け取る。

入力は `app/src/shared/ipc-inputs.ts`、保存データの構造と既定値は `data-schemas.ts` に定義する。型は Zod の `input` / `output` から導く。チャネルの戻り値は `ipc-results.ts` を main と preload の両端で使う。

`activity-ipc.ts` は全チャネルの送信元と引数を検証します。配備済みのアプリ入口、または明示した開発サーバーの最上位フレームだけを受け付けます。入力が不正な場合はハンドラを実行しません。ログにはチャネルと問題の位置・種類だけを記録し、ペイロード全体は記録しません。

DB の置換処理も共通スキーマを使う。IPC 以外に ZIP 取り込みからも呼ばれるため、検証に成功してから既存行を置き換える。省略可能な値の既定値と、不正値の読み替えは区別する。不正値を空配列へ変えて保存しない。

## 契約の変更

IPC、設定、フォルダ、タグ、プロフィール、タブ、アーカイブの保存形式を変更するときは、共通スキーマ、メインプロセス、プリロードスクリプト、レンダラーを同じ変更で更新します。不正な値を既定値や空配列に読み替えて保存しません。ZIP の整理情報は統合前に検証し、不正な値があれば DB トランザクションを戻します。

## 投稿の取り込み・復旧

投稿の保存形式・既定値と型は `native-host/post-schemas.mts` で共有する。`post-record.mts` は検証後に取得時刻を付け、画像と動画の保存先を整理する。タグ名の NFKC 正規化と重複除去は、文字列配列の検証後に行う。

一覧表示の投稿・プロフィールは `app/src/shared/post-view-schemas.ts` で保存スキーマから導く。DB の読み出し、IPC、レンダラーで同じ型を使う。ゴミ箱やタグの再計算中には存在しない集計値を、表示用の型で区別する。切り抜き範囲とメディアの型も保存スキーマを共有する。

Native Messaging の要求・応答と取得前のメタデータは `native-host/protocol.mts` に定義する。要求が不正ならダウンロードや保存を始めず、既存の失敗応答に項目の位置とエラーの種類を載せる。ペイロードの値は載せない。拡張機能の投稿型と初期値も、この共有定義から導く。

取込キューは `InboxEnvelopeSchema` でエンベロープと投稿を検証する。ハッシュは、既定値を補う前のレコードで照合する。ZIP の投稿と復元フラグは保存前に検証する。不正な投稿を含む ZIP では DB トランザクションを戻す。既にコピーした媒体ファイルは残るため、DB とファイルの操作全体がアトミックになるわけではない。

`restorePostFlags` は `PostFlagsSchema` を使う。ゴミ箱からの復元はファイルを移す前に投稿・フラグ・所属を検証する。投稿とフラグは同じ DB トランザクションで戻す。復元先のフォルダが既に削除されていた場合の所属判定は、構造検証とは別の処理として残る。

DB の JSON 列は保存時と同じスキーマで読む。破損した列やゴミ箱のレコードは警告を記録し、表示できるデータだけを返す。この読み取りで保存内容を書き換えない。新規の取り込みで不正値を欠損へ読み替えることとは区別する。

## 取得元の必須値と欠損

取得元の応答と共通の保存形式は、別の契約として検証する。取得元の仕様で認められる省略・空値は受け付け、未知の追加項目だけを理由に応答を拒否しない。届いた不正値を推測で補完したり、空の正常値へ読み替えたりしない。

取得元の契約は `extension/utils/extractor/api-schemas.ts` と `bluesky-api-schemas.ts` に定義する。Bluesky の投稿件数は公式 Lexicon で省略可能だが、本文・作成日時や投稿の識別情報は必須。X の埋め込み用 API と pixiv AJAX は公開された開発者 API ではないため、実応答にないフィールドを必須値として扱わない。X の `possibly_sensitive` は省略可能とする。X API v2 の契約を埋め込み用 API の根拠には使わない。

投稿と投稿者の識別に必要な基本情報を先に検証する。必須値の欠落や不正な JSON では、投稿情報の取得成功として扱わない。プロフィール、件数、本文の追加情報、メディア、引用、リンクカードなどは、それぞれの工程で検証してから反映する。アバターとプロフィールの追加情報も分け、一方の不一致で他方の有効な情報を失わないようにする。

工程の失敗は `acquisitionIssues` の `post`・`profile`・`media` と、`invalidResponse`・`fetchFailed`・`unavailable` で区別する。検証済みの情報を返す場合も、取得できなかった範囲を残す。メディアの一部を取得できない場合や未知の形式を受け取った場合は、正常な「メディアなし」や完全取得として扱わない。

`acquisitionComplete` は取得不足が残るレコードを不完全と判定する。再取得が不完全な場合は、保存済みの本文、プロフィール、メディアを空の値で置き換えない。完全取得と不完全取得の統合方針は、共通の保存処理で扱う。

取得の診断には固定の工程名、HTTP 状態、失敗分類、検証項目の位置を記録する。応答の値、URL、認証情報、動的なキー、例外のメッセージは転送しない。診断 callback の失敗で取得処理を止めない。

フォルダの親子関係、参照先の存在、タグの正規化・衝突、トランザクション、URL と投稿 ID の対応付けは構造検証とは別の処理として残る。

## 検証

変更に近いテストから実行します。通常は `npm run check`、拡張機能を変更した場合は `npm run check:ext`、保存経路や起動処理を変更した場合は `npm run test:integration` も実行します。配備済みのアプリまたは開発用 Chrome で確認する手順は [CONTRIBUTING.md](CONTRIBUTING.md) を参照してください。

## 根拠

入力検証と型導出は [Zod](https://zod.dev/basics)、送信元検証は [Electron のセキュリティガイド](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages)に基づきます。Zod の採用は Electron の必須仕様ではなく、このプロジェクトで選んだ実装方式です。

Bluesky の [postView](https://github.com/bluesky-social/atproto/blob/main/lexicons/app/bsky/feed/defs.json) と [post](https://github.com/bluesky-social/atproto/blob/main/lexicons/app/bsky/feed/post.json) の必須項目・省略可能項目を参照。
