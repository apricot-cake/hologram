# ライブラリ保護 設計書（バックアップ / ゴミ箱 / 編集 Undo）

> 状態: **設計確定・実装待ち（Sonnet）**（2026-06-13・Opus と対話して収束）。
> 由来: 「定期エクスポートを自己流で作り込んだ」→ 率直レビュー → 安全網の作り直し。

## 0. 方針の核

ライブラリ保護を**3つの直交した役割**に分離する。1つの仕組みで全部やろうとしない。

| 役割 | 守る対象 | 手段 |
|---|---|---|
| **バックアップ** | デバイス故障・紛失・破損（災害） | 透明な増分・最新ミラー（オフデバイス） |
| **ゴミ箱** | 誤削除 | ソフト削除＋N日保持＋アプリ内復元 |
| **編集 Undo** | 一括操作の後悔（誤った一括タグ/移動等） | in-session の Ctrl+Z / Ctrl+Shift+Z |

**やらない**と決めたもの（理由つき）:
- **版履歴（point-in-time の全体復元）** — 資産（jpg/json/media）は immutable で、唯一のリスク＝削除はゴミ箱で足りる。Photos/Google Photos はゴミ箱のみ、Lightroom も版を持つのは catalog（メタ）だけ＝同じ結論。
- **per-item の情報履歴（「この画像のタグを以前に戻す」）** — phantom need。タグのやらかしは実際には「一括操作のやらかし」で、それは item 単位ではなくアクション単位の問題（→ 編集 Undo が担当）。
- **不透明バックアップ（content-addressed 等）** — データポータビリティを尊重するため却下。バックアップは他ツールで開ける形を保つ。
- **クラウド API ネイティブ連携（OAuth）** — スリックだがソロには保守が重い。当面は「既存クラウド同期フォルダを宛先に指す」で代替（将来候補）。
- **分岐ツリー履歴・永続 Undo** — 線形・in-session で足りる。

## 1. ① timer バグ修正（最優先・小・独立）

**現状の不具合**: `armBackupSchedule`（[app/main.js](../app/main.js) 〜800）が `setInterval(fn, backupIntervalMs(b))` を直叩き。Node のタイマーは **2³¹−1 ms（≈24.8 日）超のディレイを 1ms にクランプ**するため、間隔が長いほど暴走する：
- 該当する入力: `intervalUnit:'year'`(31.5e9ms) / `'week'`×≥4 / `'day'`×≥25。
- 結果: フルライブラリ ZIP を 1ms 間隔で連続生成（mutex で同時実行は防ぐが、1本終われば即次が走る＝CPU/ディスク張り付き）。**長い間隔ほど危険＝直感の逆**。

**修正**:
- `setInterval` を廃止し、**`lastRunAt` から次回 due を算出する自己再スケジュール `setTimeout`** ＋短い heartbeat（数分ごとに「due か？」を判定）に。タイマーに巨大値を渡さない＝オーバーフロー消滅。スリープ跨ぎにも強くなる。
- 選択肢から `'year'` を外す（バックアップ周期として無意味）。`'month'` までに留める。
- ② でバックアップ機構ごと作り替えるなら、この新スケジューラに統合する。
- 起動時の overdue 取り戻し（前回から間隔以上空いていれば1回実行）は**維持**。

## 2. ② バックアップ = 透明な増分・最新ミラー（git-remote モデル）

### メンタルモデル
「第2のライブラリ」ではなく **「写し（remote）」**。canonical はアプリ固定ストレージ（`%LOCALAPPDATA%\Corpus\library`）。git の remote が「透明・clone 可能なフルコピーなのに rival に見えない」のと同じ位置づけにする：
- アプリが **subordinate な写しとして所有**する。ユーザーが選ぶ「ライブラリ」にはしない。
- UI は **ambient なステータス**として提示：「バックアップ: ON ／ N 分前に保存 ／ M 件 ／ 宛先」。開いて作業する対象ではない。

### 形
- ライブラリのサイドカー形式（`<id>.jpg` + `<id>.json` + `<id>-media-N.<ext>` + 整理 JSON）を**そのまま**宛先にミラー。**ポータブル**（他ツールで開ける＝不透明化しない）。
- **増分**: ファイルは immutable なので「宛先に無いものだけコピー」。diff 計算は不要（存在チェックのみ）。
- **最新ミラー（latest state）**: 削除は宛先からも削除して同期。版は持たない（資産は immutable ＝版不要）。
- **フル ZIP 毎回を廃止**（GB 再生成・5 重複製の解消）。ZIP は**手動エクスポート専用**に残す（可搬な 1 ファイルが要る場面用）。

### 宛先
- 外付けドライブ or **ユーザーの既存クラウド同期フォルダ**（OneDrive / Dropbox / iCloud Drive / Google Drive）。
- → **OAuth 無しで「ボタン一つクラウド」体験**。多数の小さな immutable ファイルはクラウド同期と相性が良い（一度上げたら再アップしない・巨大単一ファイルの再アップ地獄が無い）。
- メインの保存先を sync フォルダに live 書き込みする案は**不採用**（破損リスク＝%LOCALAPPDATA% に逃した理由）。同期に晒すのは**写しだけ**。

### 安全策（既存を踏襲）
- 宛先と保存先の **overlap 拒否**（入れ子/同一を弾く＝書込ループ防止）。
- アトミック書込（`tmp → rename`）。
- 宛先直下にぶちまけない（サブフォルダ強制 or 宛先自体が専用フォルダ）。

### 失敗の可視化（新規）
- 現状 `lastResult.ok` を config に書くだけ＝サイレント。**「前回失敗（理由）」を設定 UI に出す**（容量不足・権限・ロックで黙って死なせない）。

### cleanup（同梱）
- stale comment 修正: [app/main.js](../app/main.js):711「増分エクスポート」は実体フルスナップショット（W2c で置換済み・未追従）。
- 命名整理: `backup` / `export` / `Corpus-export` の重複概念を整理。
- orphan `.tmp` 掃除: 書込失敗時の `corpus-export-….zip.tmp-<n>` は prune 正規表現に当たらず残る → 起動時に掃除。

## 3. ゴミ箱（誤削除の安全網）

- **ソフト削除**: 削除を即時パージせず trash 領域へ（保存先内 `.trash/` 等。list-posts のスキップ対象に追加）。
- **復元**: アプリ内で**個別復元**（粒度が細かい＝1件だけ戻せる。版履歴の「全部巻き戻し」より適切）。
- **N 日で自動パージ**（既定 30 日想定。Photos と同等）。手動「空にする」も。
- **バックアップとの関係**: 最新ミラーは削除を伝播する → 誤削除の救済窓は「ゴミ箱の N 日」。パージ後は両方から消える（Photos 等と同挙動＝許容）。
- **UI**: 既存の削除フロー（`deletePost`）を trash 経由へ。サイドバー or 設定に「ゴミ箱」ビュー（復元 / 完全削除 / 空にする）。

## 4. ③ 編集 Undo / Redo（in-session・一括やらかし用）

- **形**: セッション内の**線形** undo/redo スタック。`Ctrl+Z` / `Ctrl+Shift+Z`。
- **対象**: 破壊的/一括の**編集** = 一括タグ付与/除去・一括フォルダ移動・連続タグ付けウィザードの一括・グループ化/解除。**削除（単発/一括）はゴミ箱が持つ**ので Undo と二重に持たない。
- **記録**: 各操作を**双方向**（do/undo 両方、または before/after）で 1 エントリ。Redo は forward を再適用。
- **ルール**:
  - 新しい編集が入ったら **redo スタックを破棄**（線形・分岐ツリーなし）。
  - 有界（直近 N 操作）。
  - **再起動でクリア**（一括やらかしの後悔は即時に来る＝ in-session で十分）。
- **整合性（重要な利点）**: in-session ＝ 参照先のタグ/フォルダは常に**現存**（たった今触ったから）→ dangling 参照・再作成プロンプト・永続化・ポータビリティの問題が**すべて回避**される。
- **戻る/進む（ナビ履歴）とは別軸**。あれはビュー状態のナビゲーションで、タブが役割を継いだため**撤去のまま**（Todoist #3）。Undo はデータ変更の取り消し＝別物。

## 5. 実装順序（Sonnet）

1. **① timer 修正** — 独立・即効・小。② に着手するなら新スケジューラに統合。
2. **ゴミ箱** — 安全網の本命・他から独立して入れられる。
3. **② バックアップをミラー方式へ** — `lib-archive` のフル ZIP は手動 export に残し、定期は新ミラー経路へ。失敗可視化・cleanup 同梱。
4. **③ 編集 Undo/Redo** — 独立・最後でよい。

各段は独立して出荷可能。安全網として効くのは 1（暴走止め）と 2（ゴミ箱）が先。

## 6. 検証

- **timer**: 長間隔（`'year'` 等・週×4・日×25）で暴走しないこと。due 計算が `lastRunAt` 基準で正しいこと。
- **ミラー**: 増分（新規のみコピー）・削除伝播・overlap 拒否・アトミック・**宛先がクラウド同期フォルダでも動く**こと。ミラーモジュールは Electron 非依存で `node` 単体テスト（`lib-archive` と同方針）。
- **ゴミ箱**: 削除 → trash → 個別復元 / 自動パージ / 空にする。list-posts がゴミ箱を拾わないこと。
- **undo/redo**: 一括操作の往復、redo-clear-on-edit、有界、再起動でクリア。

> 関連: 既存の `app/lib-archive.js`（フル ZIP・冪等 import・union merge・Zip-Slip ガード）は良質なので**手動エクスポート/インポートの基盤として維持**。本設計が変えるのは「定期＝フル ZIP」を「定期＝増分ミラー」に置き換える点と、ゴミ箱・編集 Undo の新規追加。
