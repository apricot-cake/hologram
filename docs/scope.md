# Hologram の射程

個別機能の採否は、この文書の概念モデルで判定する。実装の構成は `architecture.md`。

（#190 で確定・2026-07-20 に名乗りを改訂・段の分け方の物差しは #255 で改訂・表示の原則は #379 で追加）

## 名乗り

**ウェブのコンテンツを、出自・エンゲージメントごと保存できる個人ライブラリ。**

一級性は SNS に限らず、プラットフォームに投稿されたコンテンツ全般に及ぶ（改訂の経緯・根拠は #190 コメント）。この汎用側の選択は必然ではなく設計判断で、主要プラットフォーム対応に絞る特化も成立する却下案として #190 に記録してある。

## 概念モデル

1. **境界＝キュレーション**: 何がライブラリに入るかはユーザーの収蔵行為が決める。ファイル形式や出自で「コンテンツか否か」を判別しない。
2. **メタデータ＝勾配**: 出自があれば取得時に自動で濃く付き（プラットフォーム投稿＝投稿者・本文・日時・エンゲージメント）、無ければタグ・フォルダが受け持つ（ローカルファイル）。恩恵の差であって身分の差ではない。
3. **表示＝能力の階級**: メディア（画像・動画）はビューア・サムネイル込みのフル体験、描画できない任意ファイル（PDF・配布資料等）は「収蔵品」＝保存・タグ・フォルダ・ファイル名検索・OS 既定アプリで開く＋安価なプレビューまで（#236）。提示能力の差であって価値の宣言ではない。
4. **表示＝データからの再現**: 保存するのは投稿の素材（本文・投稿者・日時・メディア実体・エンゲージメント）であって、投稿の見た目そのもの（画面を写した画像）は保存しない。アプリ内の見た目は、表示のたびに素材から組み立てる。取得は不可逆・表示は可逆で、素材さえ揃っていれば表示は後から作り直せるため（#292・#379）。キャプチャ画像をユーザー自身が収蔵する場合は対象外＝そのキャプチャは見た目の代用品ではなく収蔵品そのもの（段2）。
5. **取込の深さは段で分ける**。次節のとおり、**段を分ける物差しと、各段の上限を決める物差しは別のもの**。

## 取込の3段構造

### 段の分け方＝フロー型かストック型か

分けるのは規約でも法でもなく、**コンテンツの性質と保存の目的**（消失前の記録という目的があるか）。

**ストック型の定義は「消えない」ではなく「再訪される設計か」**。YouTube の動画は消えうるがストック型（固定 URL を持ち、再訪され、再生数が積み上がる）。**消失可能性を段の判定に使わない。**

### 段1: フロー型のプラットフォーム投稿＝まるごと保存

SNS 投稿が代表。流れて消えるコンテンツ。

上限を決めるのは、私的使用のための複製であること・消失前の記録という正当性・市場代替の害の小ささ。

**公式の埋め込みが提供されていても採らない。** 埋め込みは表示のたびに提供元から読み込むため、元が消えれば中身も消える。段1 の目的は消失前の記録なので、埋め込みではその目的を一切果たせない。

### 段2: ローカルファイル＝実体保存

ローカル取込・要素キャプチャ等。表示は概念モデル3 の2階級で受ける。

### 段3: その他あらゆる URL＝カード保存

ストック型（プラットフォームに据え置かれ再訪される）コンテンツ。まるごと保存はプラットフォームの客足・投稿者の engagement を代替する。

上限を決めるのは**公式が用意した形**。すなわち OGP カード（タイトル・説明文・サムネ）＋ユーザー注釈（タグ・メモ）まで（#195）。**公式の埋め込みが提供されているものは公式埋め込みで受ける**（#196・動画に限らない＝埋め込みの提供自体が「客足と収益がプラットフォーム側に残る形」の公式な用意である）。実体はプラットフォームに残し、閲覧はリンク先で行う。

実例として、YouTube の利用規約は動画の複製・ダウンロードを禁じた上で、埋め込み型プレーヤーでの表示は明示的に認めている（条文の引用は #254 に保管）。#196 の「公式が形を用意している」は比喩ではなく条文そのもの。

深さの制限は実体（バイト）の話であり、カードにも出自メタデータは取れる範囲で付す。

### 規約は段を分ける物差しにならない

X・YouTube 双方の規約を確認した結果、両者は同じ構造だった（複製は提供された経路を通せ・どちらも公式埋め込みを提供）。**規約は段1 と段3 を区別しない。** 規約が働くのは段3 の中で上限を教えるところであって、段を分けるところではない。

したがって、**同じ「公式埋め込みが提供されている」という事実に対し、段によって答えが変わるのが正しい**。段1 では採らず（目的を果たせない）、段3 では採る（目的に忠実）。

## 取得の採否は表示の採否と物差しが違う

段は「どこまで保存するか」を決める。その中でさらに「届いたデータのどれを残すか」を問われたときは、**可逆かどうかで物差しを分ける**。

- **表示・検索・ファセットは可逆**＝作らなくても、実需が見えた日に作れば同じものが手に入る。だから採否は実需で判断する（この文書の他の節が扱うのはこちら）
- **取得は不可逆**＝投稿は削除され、アカウントは消える。保存時に拾わなかったものは後から取り戻せない

したがって、**追加のリクエストを要さない＝すでに手元にあるデータは、使う当てが無くても既定で全部残す**（[ADR 0011](decisions/0011-preserve-acquisition-payloads.md)）。残す先は原本の層で、正規化フィールドへ昇格させるかどうかは従来どおり実需で絞る。

**追加のリクエストを要する取得はこの原則の対象外**＝リプライ・スレッド・プロフィールのように取りに行く必要があるものは、従来どおり個別に費用対効果で判断する。

## 採否の物差しに使わないもの

**作者個人のライブラリの事情と、既存データとの後方互換は、製品判断のゲートにしない**（2026-07-11 統合改訂）。上の物差しで採ると決めたものを、この2つを理由に降ろさない。

- 作者個人のライブラリの事情（規模・件数・利用実態）に合わせて、機能の採否・優先度・据置の発火条件・性能目標を判断しない。一般ユーザーにも有用な機能、もしくは単なるライブラリの整理や修正なら可。
- 作者のライブラリに気を使って（既存データとの互換維持などを理由に）**設計を歪めない**。
- **リリース前につき「他人のライブラリ」は存在しない**＝既存ユーザーデータとの後方互換・移行コード・旧名の焼き付きを理由に、命名や設計を妥協しない。
- 手元ライブラリを壊さないための一回きりの移行手順は、設計でなく**作業手順**として可（リリース前に撤去してよい仮設コードとして隔離する）。適用例は [ADR 0010](decisions/0010-sqlite-as-the-metadata-truth-source.md)・[ADR 0025](decisions/0025-database-lives-inside-the-library-folder.md)・[ADR 0028](decisions/0028-startup-storage-redirect-guard.md)。

## 射程外

**目標になり得たが、意図的に外したもの**を並べる。「できないこと」の一覧ではない。

- **テキスト主役コンテンツ（記事・小説）専用の UI**（リーダー・本文抽出）。段3 の上限はカード＋注釈で、本文を抱えることはこの上限を超える。リリース後の再検討は可（#190）。
- **汎用ファイル管理（DAM）への主役の入れ替え**。任意ファイルは収蔵するが（概念モデル3）、「なんでも入る × 強力な検索」を看板にはしない。検索の強さを支えているのはプラットフォーム投稿の構造化メタデータであり、それが最も薄い対象を看板に据えることになるため（#190）。
- **購読・巡回による自動収集**。フィードを購読して自動で溜める形は、何がライブラリに入るかをユーザーの収蔵行為が決めるという境界（概念モデル1）を手放すことになる。取り込みは常にユーザーが起点。
- **投稿の見た目そのもののアーカイブ**（保存時点の実レンダリングを画像として残す）。残すのは素材とその出自で、見た目は素材から組み立てる（概念モデル4）。手放すのは当時の実フォント・実レイアウトに限られ、投稿の中身は素材から再現する（#379）。
