# 0026. ローカル ML 基盤の3つの線引き（モデルの置き場と入手経路・派生データと真実源の境・オプトインの掛かる範囲）

## 背景

カラー検索・OCR・AI タグ提案・ビジュアル検索の4機能は、どれも「ライブラリを全件舐めてローカルで解析する」という同じ形をしている。4回別々に作ると、モデルの置き場も解析結果の置き場も全件走査も4通りになり、同意の扱いだけが機能ごとに揺れる。

そこで土台を1回だけ作った（#98・工程5本が 2026-08-03〜08-05 に着地）。土台を入れると、それまでこのアプリに無かったものが3つ増える。

1. **アプリが配らないバイナリ**（モデル）＝どこに置き、どこから取り、どう捨てるか。
2. **再構築できるデータ**（解析結果）＝真実源と同じ扱いにすると、壊れた時に「どちらが正しいか」を決める規則が要る。
3. **ユーザーの同意という前提**＝アプリ本体が外部へ接続するのはモデル取得が初めてで、解析は本人の許可があって初めて走る。

この ADR は、その3つについて決めた線だけを残す。工程ごとの受け入れ条件・実測値・検討過程は各 Issue にある。

## 決定1: モデルは端末資産として設定ディレクトリに置き、取得だけを自前で持つ

- **置き場は `~/.hologram/models/<org>/<name>@<rev>/`**（`lib-ml-runtime.ts` の `modelsRoot()`＝`configDir()/models`）。保存フォルダの外に置く＝バックアップ（#233）とエクスポート（#57）は保存フォルダしか歩かないので、モデルがそこへ紛れ込む経路が構造的に無い。**ADR 0025 が `hologram.db` をライブラリの中へ移した後も、モデルは外に残る**＝DB はそのライブラリの一部だがモデルは端末の資産で、ライブラリをコピーした時に付いてこない方が正しい。
- **`rev` は Hugging Face のコミットハッシュで固定する**。ブランチやタグは使わない＝同じアプリのビルドが日によって違うバイトを引かないため。
- **推論・前処理・モデル配置の流儀は `@huggingface/transformers`（transformers.js）に寄せ、取得だけ自前に残す**（`lib-model-fetch.ts`）。理由は2つ。①**SHA-256 検証を差し込む場所がライブラリ側に無い**（取得がライブラリ内で完結する）②**取得経路を同意ゲートの内側へ1本化する**＝ライブラリに取らせると「推論を呼んだ瞬間に、モデルが無ければ黙って取りに行く」経路が残り、「AI 機能を有効にした時に限り接続する」という説明が破れる。推論側は `env.allowRemoteModels = false` を立て、通信を封じてある。
- **コード内レジストリが真実源**（`lib-model-registry.ts`）＝`{ id, rev, files[{path, sha256, bytes}], licenseNote }`。THIRD-PARTY-NOTICES.md と設定「AI機能」ページの表示はここから出る（同期は `scripts/model-registry.test.ts` が検査）。ハッシュは採録時に実測して焼き込む＝取得元から都度もらうと、検証が「検出したいはずのズレと同じ値」を基準にしてしまう。
- **rev が上がっても自動更新しない**。別 rev がディスクに在ることは `installedRev` として知らせるだけで、取得は再同意で始まる。`<name>@<rev>` で分けてあるので、断った人はそのまま使い続けられる。
- **推論側はモデルを絶対パスのディレクトリで受ける**（Hugging Face の repo id では渡さない）＝transformers.js が `env.localModelPath` を前置するのは repo id の形に合う文字列だけで、`@` を含むこのレイアウトは判定を通らず CWD 相対に解決されてしまう。絶対パスなら判定ごと迂回でき、命名規則をモデルマネージャ側に閉じたままにできる。ランタイムが持つのは「`modelsRoot()` の外を拒否する」ことだけ。

## 決定2: 派生データは別ファイルの SQLite に置き、真実源には1行も書かない

- **`~/.hologram/derived.db`**（`hologram.db` とは別ファイル・better-sqlite3 ＋ Kysely＝既存スタックのまま）。解析出力を `posts` 系のテーブルへ混ぜない。
- **「再構築できる側」と「真実源」で復旧規則を変える**＝`derived.db` は `quick_check` が通らなければ**捨てて作り直す**（`openDerivedDatabase`）。`hologram.db` が同じ状態なら `DatabaseCorruptError` を投げて人の判断を仰ぐ。1つの DB に同居させると、この2つの規則を「このテーブルは真実源ではない」という約束事だけで分けることになる。
- **完全撤去はファイルの削除**。消してもライブラリは1件も失われない。
- **キーの約束は `captureId` ＋ `assetRef`（`image` / `video` / `file` / `media[seq]`）＋ `segment`**（PDF はページ番号 0..N-1、静止画は 0）。1レコードが複数の実体を持ちうることと、1実体が複数ページを持ちうることの両方に対応する。本基盤が出したのは全ジョブ種が共有する `derived_progress` 1本だけで、その主キーは `(captureId, assetRef, jobKind)`、セグメントは `indexedSegments` / `totalSegments` として持つ。機能ごとのテーブルは各機能 Issue が同じ規約で足す。
- **各行に `modelId` / `modelRev` を刻む**＝出自ラベルの根拠であり、モデルを替えた時に作り直す行を選び出す手段でもある。**モデルを使わないジョブの行は両方 null**＝「AI 由来ではない」ことがデータ側の事実として残る。
- **レコードの完全削除と連動する**（`purgeDerivedForCapture`）＝ゴミ箱にある間は残し、完全削除で消す。SQLite に DB を跨ぐ外部キーは無いので、`posts` の `ON DELETE CASCADE` の代わりをコードで置く。
- **索引の進捗は結果から導き、別のカーソルを持たない**＝どこまで済んだかは `indexedSegments` / `totalSegments` そのもの。二重に状態を持つと、片方だけ消えた時にどちらが正か決まらない。
- **検索への合流は投影であって隔離の例外ではない**＝全文検索へ入るテキストは派生ストアからいつでも作り直せ、完全撤去で空になり再有効化で再投入できる（`posts_fts` は1ポスト1行のまま。ページ番号は派生ストアが持ち、提示の側で使う）。

## 決定3: オプトインは「モデルを使うジョブ」に掛ける（キュー全体ではない）

- **設定は `ai.enabled` 1つだけ**（既定オフ・端末単位＝ライブラリ単位ではない）。main は `aiFeaturesEnabled()`、設定 UI は同じ `cfg.ai.enabled` を読む。機能ごとのオン/オフは各機能 Issue が自分で足す。
- **ゲートはジョブ種の属性 `requiresModel` に掛かる**。**パーサは モデルではない**＝PDF のテキスト層抽出のような非 ML の処理を AI 機能の同意に巻き込むと、「中身を検索したいだけなのに AI へ同意させられる」という、原則の趣旨（AI を黙って走らせない）から外れた要求になる。非 ML ジョブは同意なしに動き、その出力に「AI 由来」ラベルを付けない（付けると嘘になる）。
- **透明性9項目（#98）が掛かるのは `requiresModel: true` の集合**。ただし**派生データの隔離と撤去は AI / 非 AI で割らない**＝ユーザーから見た「解析データを消す」の対象は、AI 由来かどうかで割れない。
- **ゲートは独立に3か所で閉じる**＝①索引の計画（`planRecord` が `ai-disabled` で落とす）②推論プロセスの起動（`startMlRuntime`）③モデルの取得（`downloadModel`）。1本の判定を3か所が参照する形なので、どれか1つを新しい呼び出し元が忘れても他の2つが止める。
- **オプトイン前は設定「AI機能」ページ以外に AI 由来の UI を一切出さない**（機能 UI・案内バナー・空状態からの誘導を含む）。
- **有効化したら全件を再計画する**＝`ai-disabled` で飛ばした事実はどこにも記録しない（記録すると、同意の状態と索引の状態という2つの真実ができる）ので、フルバックフィルで判定し直す。

## 影響

- **アプリ本体が外部へ接続するのはモデル取得が初めて**＝PRIVACY.md に通信の一覧、THIRD-PARTY-NOTICES.md にモデルのライセンスを持つ。どちらもレジストリと突き合わせる検査がある。
- **配布物が太る**＝インストーラ 113.0MB → 145.1MB（+30.6MiB・#831 実測）。onnxruntime-node のプリビルドは win32-x64 だけを残し、onnxruntime-web の `dist` は2ファイルだけ拾い直している。⚠️**`npm run check` はこの経路を1バイトも踏まない**＝配布形を触ったら `npm run dist --workspace=app` の後に `node scripts/test-ml-runtime.cts --exe ...` を回す（docs/build.md）。
- **本基盤はラスタライザを持たない**＝索引の入力は既存設備から取る（視覚系はサムネイルキャッシュ、OCR は原寸）。PDF のページ画像は #740 の描画設備待ちで、それまでは「未索引」（`indexedSegments < totalSegments`）として残り、着地後のバックフィルが残りだけを拾う。
- **全件走査は1本だけ**＝ジョブプール（`lib-job-pool.ts`）はサムネイル生成のプールを一般化したもので、背景ジョブは対話的な仕事が1つも待っていない時にだけ開始される。サムネイル側の入場規則は変わっていない。
- **撤去・再構築・鮮度表示の UI は #100（ライブラリ健全性ダッシュボード）が受け皿**＝実処理は #832 / #833 が持つ。
- **機能側（#48 / #49 / #50 / #51）がやること**は、ジョブ種を1つ登録し、`derived.db` に自分のテーブルを1つ足し、必要ならレジストリにモデルを1件足すこと。並列度・優先度・停止・上限・同意・出自の根拠は、もうこの土台にある。

## 標準の照合（一次ソース確認は各工程 Issue の起票時）

- **digiKam / Firefox の翻訳 / Immich** — ローカル推論を持つ実プロダクトは「同梱せず・利用者の操作で取得し・撤去できる」で一致している。digiKam は「全ての AI 機能はこのコンピュータの中だけで動く」と明記し、Firefox は撤去できることを機能の一部として扱う。Immich は Hugging Face Hub から必要時に取得してキャッシュへ置く。
- **paperless-ngx** — 先頭 N ページだけ OCR する設定（`PAPERLESS_OCR_PAGES`）と、テキスト層のあるページを飛ばす設定（`PAPERLESS_OCR_MODE=auto`）を持つ＝上限とスキップを設定として持つのが定石。
- **Zotero** — 全文は添付アイテム単位の1本のテキストとして持ち、ページは `indexedPages` / `totalPages` という**索引の進捗メタデータ**として別に持つ＝「索引はアイテム単位・ページは付随情報」。
- 「コミットハッシュで固定し SHA-256 で検証する」ところまで公開仕様として書いているデスクトップ製品は**確認できず**。

## 却下した案

- **モデルの取得も transformers.js に任せる** — SHA-256 検証を差し込む場所が無く、推論を呼んだ瞬間にネットワークへ出る経路が残る（同意の説明が破れる）。逆に**推論・前処理まで自前で書く**のも却下＝トークナイザ・画像の正規化・出力の後処理がモデルを増やすたびに増える。
- **Hugging Face の API からファイルの sha256 を都度取って検証する** — 検証の基準を取得元からもらうことになり、固定した意味が薄れる。
- **タグ（`main` / `latest`）でモデルを追う／1つのディレクトリに上書きしていく** — 前者は同じアプリが日によって違うモデルを引き、後者は再同意の前に挙動が変わる。
- **派生データを `hologram.db` にテーブルとして足す** — 撤去がテーブル削除になり「消し切った」ことを示しにくく、DB 世代スナップショットが派生データで太る。
- **保存フォルダの `.derived/` に jsonl ＋ bin を自前で持つ**（#98 の原案） — 保存フォルダはクラウド同期先になりうる（ADR 0010 / 0025 の警告の対象）＝再構築できるものを同期させる価値も無い。追記専用ファイル＋ tombstone ＋コンパクションは、別ファイルの SQLite なら `DELETE` と `VACUUM` が既にやる。
- **バックフィルの進捗を別ファイル／別テーブルに持つ** — 結果の有無から導けるものを二重に持つと、片方だけ消えた時にどちらが正か決まらない。
- **キュー全体をオプトインで止める** — 非 ML の抽出まで AI 機能の同意に巻き込むことになる（決定3 の理由）。
- **機能ごとにキューを持つ** — 4機能が同時に全件走査を始めて UI を潰す。
- **推論を main プロセスで直接走らせる** — セッション生成とテンソル整形は同期的に長く走り、IPC とウィンドウが止まる。ネイティブ層のクラッシュがアプリごと落ちるのも避けたい（`utilityProcess` へ分離した理由）。
- **索引の対象集合を `assetClass` で切る** — #236 の2階級は**提示能力**の区分であって索引対象の区分ではない。対象は「入力を作れるか」で切る。
- **OS のシェルサムネイルが絵を返した収蔵品を視覚系ジョブに載せる** — 入力がマシン依存になり、同じライブラリを別の PC で再構築すると違う派生データが出る＝`modelRev` で再現性を担保する設計と噛み合わない。
- **アーカイブ（zip / 7z / rar / tar）の中身を開いて索引する** — 自動で無人で走る処理へ zip bomb とパストラバーサルの攻撃面を持ち込まない。やるならユーザーの明示操作を入口にする。
