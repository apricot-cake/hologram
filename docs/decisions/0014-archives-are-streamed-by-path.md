# 0014. アーカイブはバイト列でなくパスで受け渡し、main が fd からストリームする

- 状態: 採用（2026-07-29）
- 関連: #485（インポートの yauzl 化）・#322（旧形式インポートの去就）・#506（うごイラ再生に残る jszip）

## 背景

ライブラリ全体を1つの ZIP に書き出し、そのまま読み戻せることが移行・バックアップの土台になっている。当初の実装は書きも読みも JSZip で、**アーカイブ全体を1つの Buffer に載せる**設計だった。ここには2つの上限があった。

1. **メモリ** — 6.75 GiB / 18,337 ファイルのライブラリで書き出し時のピーク RSS が 11.5 GiB。16 GiB の機械ではアプリ常駐と合わせて OOM になり、主プロセスがハングした。
2. **ZIP64 非対応** — 4 GiB を超えると central directory のオフセットが 32bit で桁あふれし、**壊れて開けない ZIP** ができる。

インポート側にはもう1つあった。レンダラーがファイルを `arrayBuffer()` で丸ごと読み、バイト列を IPC で main へ渡していた＝大きな書庫ではレンダラーが先に落ち、落ちなくても IPC メッセージが成立しない。

## 決定

**ZIP の入出力は main が fd から行い、レンダラーにも IPC にもアーカイブのバイト列を流さない。**

- 書き＝**yazl**。`addFile` はエントリを書く瞬間にソースを読むので、常駐は約1エントリ分。ZIP64 を出せる。
- 読み＝**yauzl**。中央ディレクトリを fd からランダムアクセスで読み、エントリごとにストリームを開く。ZIP64 を読める。
- **書庫はパスで渡す**。書き出し先は `dialog.showSaveDialog`、取り込み元は `dialog.showOpenDialog` — どちらも main が持ち、レンダラーが受け取るのは結果（件数・成否）だけ。**「完全形式か旧形式か」の判定も main が行う**（判定のためだけにレンダラーがファイル全体を開いていた）。

実測（2026-07-29）: 4.39 GiB の完全 ZIP を書き出し、4 GiB 境界の先に置いたエントリを読み戻せる。取り込み中の RSS は 92 MiB のまま動かない。

### untrusted な書庫を読むときのガードは2層

書庫は機械間で手渡しされる＝細工されたものが来る前提で読む。yauzl へ移ったことで防御が2層になり、**層ごとに結末が違う**ことを設計として引き受ける。

| 層 | 何を見るか | 結末 |
|---|---|---|
| 1: ライブラリ自身の名前検証 | 絶対パス・ドライブレター始まり・`..` セグメント・バックスラッシュ | **書庫まるごと拒否**（エントリを1件も渡さない＝1バイトも書かれない） |
| 2: こちら側のパス規則 | library 直下は1セグメント、例外は `avatars/<name>` の1段だけ | **エントリ単位で skip**（同じ書庫の正当なエントリは取り込む） |

層1は library 側が持つので、層2は「library 側が通す形」だけを見ればよい — が、**層2を層1で代替しない**。正当な書き出しが出す名前の形はこちらしか知らないし、読み手を替えたときに層1の内容は変わる。

展開量のガード（エントリ数・エントリ単体・合計）は**書庫が申告する値**で先に判定し、1バイトも展開せずに拒否する。加えて**実際に流れたバイト数でも打ち切る**＝申告を偽った書庫に対しては、こちらが読んだ量そのものが上限になる。

## 影響

- `app/src/main/lib-archive.ts` が ZIP の入出力を一手に持ち、レンダラーからは ZIP リーダが消えた（残る2箇所は #322 と #506）。
- 進捗表示は書き出しストリームのバイト数から出る（`export-progress` IPC ＋ タスクバー）。取り込み側に同じものは無い。
- **エントリ数の上限は end-of-central-directory の申告値で判定する**＝中央ディレクトリを1レコードも読まずに拒否できる。過少申告しても読み手はその件数しか渡さないので、走査中の再カウントは原理的に発火しない（置くと死んだガードになる）。
- 回帰テストの「爆弾」は**本物の ZIP の中央ディレクトリを書き換えて**作る。GiB 級の実データを用意せずに、production と同じ経路を踏ませるため。

## 却下した案

- **JSZip のまま上限だけ足す** — ZIP64 を出せない以上、4 GiB 超のライブラリは書き出した時点で壊れる。メモリだけの問題ではない。
- **レンダラーで開いて判定し、main へバイト列を渡す（従来）** — 判定のために全量を読む必要があり、大きな書庫では判定にすら到達しない。
- **archiver / adm-zip などの高水準ラッパ** — yazl/yauzl はこの2つが土台にしている層で、間に挟まる分だけストリームの寿命とエラー経路が見えにくくなる。ここで欲しいのは「いつ読むか・いつ止めるか」を自分で決められることだった。
