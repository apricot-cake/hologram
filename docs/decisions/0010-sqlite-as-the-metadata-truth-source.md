# 0010. メタデータの正本を SQLite に置き、ファイルは実体だけを持つ

- 状態: 採用（2026-07-28）／**「データベースは保存フォルダの外に置く」条項のみ [0023](0023-database-lives-inside-the-library-folder.md) へ置き換え（2026-08-03）**。この節を含む決定本体（正本を SQLite に置く・単一ライター・移行の進め方）は今も有効
- 関連: [#5](https://github.com/apricot-cake/hologram/issues/5)（St0〜St9＝#293〜#302）・[#176](https://github.com/apricot-cake/hologram/issues/176)（DB配置の改訂）・[0002](0002-dependency-adoption-criteria.md) 依存を入れる基準

## 背景

当初は投稿1件につき画像とメタデータ JSON を1つずつ保存フォルダへ並べ、アプリは起動のたびに全ファイルを読んで一覧を組み立てていた。この形は数千件までは素直に動くが、次の3つが件数に比例して伸びる。

- 起動時の全量スキャン（1万件で約1.5秒、3万件で約4.3秒）
- 検索の線形走査（全レコードを総当たりで照合）
- 一覧の IPC 転送（レンダラーへ全件を毎回シリアライズ）

加えて構造的な問題があった。ファイルが正本だと、書き込みはプロセスの数だけ存在する（アプリ・ブラウザ拡張から呼ばれる常駐プログラム）。整理層は1ファイルを丸ごと上書きする形だったため、2つが同時に書けば後に書いた方が相手の変更を黙って消す。複数ウィンドウ（#32）はこれを日常的に起こす。

## 決定

**メタデータの正本を SQLite データベース1つに置く。** 画像・動画・アバターと、ゴミ箱の中身はファイルのまま。

- **エンジンは better-sqlite3 ＋ Kysely**。全文検索（FTS5）が同梱で、日本語の部分一致に必要な trigram トークナイザが使える。Kysely は公式の SQLite 方言を持つ
- **書き手はアプリのメインプロセスだけ**（単一ライター）。別プロセスは保存フォルダの取込キューへ追記し、アプリがそれを取り込む
- ~~**データベースは保存フォルダの外**（設定ディレクトリ）に置く。保存フォルダはユーザーがクラウド同期フォルダに向けうる場所で、書き込み中のデータベースを同期クライアントに触らせない~~ → **[0023](0023-database-lives-inside-the-library-folder.md) が置き換え**（2026-08-03）＝データベースは保存フォルダの中に置く。クラウド同期の危険は配置でなく警告（save-folder-guard.ts）で処理する
- **人が読める形・持ち出しの受け皿はエクスポート**。完全 ZIP には投稿ごとの JSON をデータベースから再生成して同梱する＝ディスク上のライブラリには第二の正本を作らない
- **既存ライブラリの取り込みは一回きりの移行**とし、リリース前に撤去する仮設コードとして隔離する（#441 で撤去済み＝アプリは保存フォルダの投稿JSONを読まない。ただし孤児回復だけは例外で、実体だけが残った投稿の `<captureId>.json` を最後の手がかりとして読む＝#511）

移行は Parallel Change（expand–contract）で進めた。まずデータベースをファイルから導出される索引として並走させ、次に読み取りを移し、最後に書き込みの所有権を移した。各段が単独で動く状態でマージでき、反転までは常にファイルが正本のままなので、どの段で問題が出ても戻れる。

## 影響

- 起動が1桁速くなり、伸び方も緩くなった（3万件で 4343ms → 478ms）。全文検索は 3万件で 4.2ms
- 「起動を速くするための派生ファイル」（旧 `.index.json`）が不要になった。**移行前の warm 起動より移行後の cold 起動の方が速い**
- 後勝ち消失が構造的に起きなくなった＝複数ウィンドウの前提が整った
- 単一ファイルの破損が単一障害点になるため、対策を設計に含めた＝バックアップ世代へのスナップショット組み込み・起動時整合チェック・実体とレコードの相互照合（orphan 検出）・取込キューの保持による再構築
- ライブラリのフォルダは「実体とゴミ箱と取込キュー」だけになった。フォルダを覗いて中身を把握することはできなくなり、その役はエクスポートが担う

## 却下した案

- **node-sqlite3-wasm**（当初の候補）— ネイティブモジュールが Electron でロードできるかを実証できたので、速度とコミュニティ規模で勝る better-sqlite3 へ差し替えた
- **ファイルのまま持って索引だけ足す** — 実際にやっていた形（`.index.json`）で、起動は速くなるが後勝ち消失も検索の線形走査も残る。索引が壊れたら作り直せる代わりに、正本が複数プロセスから書かれる構造は変わらない
- **サイドカーとデータベースの併存**（両方に書く）— 二重の正本は必ずずれる。ずれた時にどちらが正しいかを決める規則を作るくらいなら、一方を捨てる方が単純
