# 0012. ライブラリのファイルを「文書」にしてよいのはラスタ画像だけにし、asset 応答自体にも CSP を載せる

- 状態: 採用（2026-07-29）
- 関連: [#215](https://github.com/apricot-cake/hologram/issues/215)・[#7](https://github.com/apricot-cake/hologram/issues/7) `app://` への移行・[#79](https://github.com/apricot-cake/hologram/issues/79) ピン留めミニビューア・[#32](https://github.com/apricot-cake/hologram/issues/32) 複数ウィンドウの許可

## 背景

保存フォルダは任意の場所に置けるので、ライブラリの画像は独自スキーム `asset://` で配る。これは `standard: true, secure: true` で登録されていて、**`asset://img/*` はライブラリ全体でひとつのオリジン**になる。

ここに「文書」が立つと話が変わる。画像を単独ウィンドウで開く経路（`open-image-window`）はライブラリのファイルを**トップレベル文書**として読み込むが、ラスタ画像なら Chromium が用意する受け身の画像ビューになるのに対し、SVG は `<script>` と `onload` を持てる本物の XML 文書として動く。ウィンドウの `sandbox: true` はここでは効かない＝あれが落とすのは Node と IPC で、ページ内の JS ではない。

結果として、スクリプト入りの SVG がひとつライブラリに紛れ込めば、それを開いた瞬間に「同一オリジン fetch で隣のファイルを読む」と「外部へ送る」が両方そろう。実測でも、対策前の状態で SVG 内のスクリプトが隣のファイルを読み、その中身を外部エンドポイントへ送るところまで通った。

到達経路は当時なかった（ブリッジは公開されているが呼び出し元が無い）。ただし機構自体は生きていて、「別ウィンドウで開く」を配線した日に穴になる。

## 決定

**入口と応答の2種類で塞ぐ。** どちらか片方ではなく両方置く＝入口だけでは入口が増えた日に守るものが無くなり、応答だけでは「スクリプトが走らない SVG 文書」という無意味な状態を許すことになる。

- **入口: `asset://` のトップレベル文書になってよいのはラスタ画像だけ**（jpg / jpeg / jfif / png / webp / gif / avif）。判定は共有の述語ひとつ（`library-files` の `isViewerImageName`）が持ち、**`open-image-window`（窓を開く経路）と `will-navigate`（トップレベル遷移の経路）の両方が同じ述語を通す**＝入口ごとに別の許可リストを持たない。拒否は例外でなく `false` の返却で表す（クリップボードが読めない形式を拒む既存の作法と同じ形）
- **応答: `asset://` の応答すべてに CSP を載せる**（`default-src 'none'` を基底に、絵として成立させるための img / media / style / font だけを開ける）。**誰が開いた文書かに依存しない**のがこの層の要点で、将来の呼び出し元は何もしなくてもこの policy を受け取る。あわせて `nosniff`＝content-type は拡張子から決めているので、中身で読み替えられないようにする
- **`<img>` や CSS 背景の表示は変わらない。** 応答の CSP が縛るのは**その応答から作られた文書**であって、その絵を貼っている側の文書ではない。SVG も絵として貼る分には従来どおり表示できる（受け身の画像としての SVG は Chromium がスクリプトを走らせない）

### 前例

この2層はどちらも Electron 公式のセキュリティチェックリストがそのまま挙げている項目で、独自の発想ではない＝**7. Define a `Content-Security-Policy`**（「制限的な規則を使う」と明記）と **13. Disable or limit navigation**（`will-navigate` を許可リストで判定する）。Hologram 側の中身は、その2つを `asset://` という自前のスキームに当てはめただけになっている。

## 影響

- **単独ウィンドウで開けるのはラスタ画像だけになる。** 動画・zip（pixiv うごイラの原本）・SVG はこの窓の対象外＝もともと静止画ビューアなので機能の欠落ではないが、「何でも開ける窓」ではなくなった
- **`asset://` へのトップレベル遷移も同じ許可リストで絞られる。** 以前は `asset:` なら何でも通っていた
- **今後この窓を使う機能（[#79](https://github.com/apricot-cake/hologram/issues/79) ピン留め・[#32](https://github.com/apricot-cake/hologram/issues/32) 複数ウィンドウ）は、この制約の中で設計する。** 独自の UI を持つビューアを作るなら、それはレンダラの文書であって `asset://` の文書ではない
- **[#7](https://github.com/apricot-cake/hologram/issues/7)（`app://` への移行）に条件がひとつ増える。** レンダラを独自スキームへ移すと、レンダラとライブラリのオリジンの関係が変わる＝移行時にこの決定を読み直す
  - **2026-08-02 に読み直し済み＝この決定は無改修のまま成立している**（[ADR 0022](0022-renderer-served-from-app-scheme.md)）。レンダラは `app://bundle` になり、以前の「`file://` のページは `asset://` を fetch できない」という依存は、**別オリジンであること＋`asset://` に `corsEnabled` が無いこと＋レンダラ CSP の `connect-src` に `asset:` が無いこと**の3つに置き換わった。入口の許可リストも応答 CSP も変えていない

## 却下した案

- **`.svg` を `text/plain` で返す** — トップレベルでの実行は止まるが、`<img>` で貼っている SVG が表示できなくなる。攻撃面の対処のために正常な表示を壊す交換になっていて、しかも守備範囲は SVG に限られる（明日 Chromium が別の形式を能動的に扱い始めたら効かない）
- **`.svg` に `Content-Disposition: attachment` を付ける** — 「開かない」が「ダウンロードのダイアログが出る」に変わるだけで、絵として表示する経路にも影響しないため何も守らない。トップレベル遷移を保存操作にすり替えるのは、利用者から見て説明がつかない
- **未使用の `openImageWindow` ブリッジごと削除する** — 攻撃面はいちばん小さくなるが、**穴はブリッジではなくスキームの側にある**。消しても `asset://` に文書が立つ可能性は残り、次に窓を配線した人が同じ穴を作り直す。塞いだつもりで塞いでいない状態がいちばん悪い。加えて、この窓は設計された操作（カードの中クリック）で、[#265](https://github.com/apricot-cake/hologram/issues/265) の実機検証で機構が生きていることも確認されている
- **CSP に `sandbox` を足して不透明オリジンにする** — 同一オリジン fetch そのものを消せるので理屈上は最強だが、Chromium が組み立てる画像ビュー文書が同じ制約下でどうなるかまで抱え込むことになる。`default-src 'none'` の時点で fetch も接続も落ちているので、得られる差分に対して代償が大きい
