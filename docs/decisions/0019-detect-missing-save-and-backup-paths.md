# 0019. 保存先・バックアップ先はパスの実在を検証し、消失を静かに再作成しない

- 状態: 採用（2026-07-31）
- 関連: #37

## 背景

保存先フォルダ・バックアップ先フォルダのパスは、外部操作（移動・リネーム・ドライブの取り外し）で実在しなくなっても、アプリ側は無検証だった。`getSaveFolder()` は config の explicit 値をそのまま返し、起動時の mkdir は既定フォルダにしか掛からない。結果として、保存先を監視し直す処理（`watchInboxFolder`）が実在しないフォルダを**空のまま黙って再作成**してしまい、取込系 IPC の `mkdirSync` も同様に再作成しうる。バックアップも宛先フォルダの実在を見ずに `mkdir({recursive:true})` していた。#302 でレコードの正本が DB（保存先フォルダから独立）へ移った後は、フォルダが無くてもレコード一覧自体は返るため、症状は「空のライブラリに見える」ではなく「投稿は並ぶがサムネイルが全部壊れる」という別の静かな失敗として現れる。

## 決定

- **起動時、explicit な保存先が実在しなければ `missing` 状態とする**。mkdir しない・既定フォルダへフォールバックしない。判定はネイティブホストと共有の純関数（`native-host/config-recovery.mts` の `libraryIsMissing`）。
- **`missing` 中は書き込み系 IPC を拒否する**（全削除・ZIP/画像/クリップボードからの取込・既存の移行「保存先を変更」）。`clearAllBlockReason` に `missing` 理由を追加し、既存の `corrupt`/`lost` と同列に扱う。
- **UI は専用の画面で置き換える**（`empty/LibraryMissingState.tsx`）。DB 由来の投稿一覧は保存先の実在に関わらず返るため、既存の「空のライブラリ」画面（`libraryEmptyVariant`）には乗せず、投稿の有無に関係なく表示を差し替える。旧パスを表示し、「再試行」（実在チェックのやり直し）と「フォルダを再指定」を提供する。
- **「フォルダを再指定」＝repoint を新設**（コピーを伴わない config 書き換えのみ）。既存の「保存先を変更」はコピー移行（現在の保存先から読み出す）が前提で、消失時は読み出し元が無い。選択先にライブラリの手がかり（`.trash`／`.hologram-inbox`／メディアファイル）が無ければ確認ダイアログで警告する。
- **バックアップは送信元・宛先の双方の実在を検証する**。宛先の親フォルダが無ければ `mkdir` の前に拒否する（`dest-missing`）。送信元（保存先）が無ければ「空のライブラリを正常にバックアップした」という誤った成功を書かず拒否する（`src-missing`）。
- **実行時検知は起動時チェック＋明示操作（再試行・repoint）の再チェックのみ**。専用のポーリングは追加しない（`fs.watch` はフォルダ消失を通知せず、常時 stat する価値も薄い）。

## 影響

- `getSaveFolder()` 自体は変更しない（explicit 値をそのまま返す既存の契約を保つ）。実在検証は呼び出し側（起動シーケンス・書き込み系 IPC・バックアップ）が個別に行う。
- `get-library-status` IPC は毎回 `statSync` する生の判定で、キャッシュされたフラグではない。

## 却下した案

- **消失時にデフォルトフォルダへ自動フォールバック / 旧パスを mkdir で再作成**: 却下。どちらも「空のライブラリが正常に開いた」ように見せ、2026-06-23 のライブラリ消失事故と同じ症状を再生産する。
- **専用の存在監視ポーリング**: 却下。実害が出るのは読み書きの瞬間なので、その場で検知すれば足りる。
- **repoint を既存の移行（relocate）で兼ねる**: 却下。移行はコピー元の実在を前提にしており、消失時の前提を満たせない。
