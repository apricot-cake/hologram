# 0023. データベースはライブラリ（保存フォルダ）の中に置く

- 状態: 採用（2026-08-03）／[0010](0010-sqlite-as-the-metadata-truth-source.md)「データベースは保存フォルダの外（設定ディレクトリ）に置く」条項の置き換え
- 関連: [#176](https://github.com/apricot-cake/hologram/issues/176)（複数ライブラリの切り替え）・[#233](https://github.com/apricot-cake/hologram/issues/233)（バックアップ基盤の再編）・[#37](https://github.com/apricot-cake/hologram/issues/37)（パス変更検知・repoint）

## 背景

0010 は `hologram.db` を設定ディレクトリ（保存フォルダの外）に置くと決めた。理由は「保存フォルダはユーザーがクラウド同期フォルダに向けうる場所で、書き込み中のデータベースを同期クライアントに触らせない」。

複数ライブラリの切り替え（#176）を設計する段になって、この配置が前提を壊していることが分かった。

- **DB の世代スナップショット（#233）はすでに保存フォルダの中に住んでいる**（`.db-generations/`、`.trash`・`.hologram-inbox` と並ぶ）。復元元のバイト列については、0010 の「クラウド同期から隔離する」という条項はとっくに適用されなくなっていた。設定ディレクトリに残っていたのは「ライブ書き込み中の1ファイル」だけ。
- **保存フォルダを切り替える機能（#176）と DB が1台に1つしかないことが両立しない。** ライブラリ A を開いたまま保存フォルダだけ B に向けても、投稿・タグ・フォルダ・タブ（すべて DB のテーブル）は A のまま残る——「ライブラリを開き直す」ではなく「メディアの参照先だけ変わる」という壊れ方になる。
- **今日の実装はすでにライブラリを跨いで混線しうる。** #37 の repoint（保存フォルダのポインタだけ書き換える）を使った後、DB の世代は「現在の保存フォルダ」へ積まれ続ける。DB を失ったときの復元は「現在の保存フォルダの世代」を最優先で選ぶため、別ライブラリ由来の世代から復元される経路がすでに存在した。

## 決定

**`hologram.db`（と `-wal`/`-shm`）をライブラリフォルダ（保存フォルダ）の直下に置く。** 設定ディレクトリには端末固有の設定（ライブラリ一覧・UI 設定・thumb-cache・ログ）だけが残る。

- **ライブラリはこれで自己完結する**＝メディア・DB・世代スナップショット・取込キューが同じフォルダに収まる。フォルダをコピーすればライブラリのコピーになり、ライブラリの識別子自体も DB の中（`store_state.libraryId`）に持たせられる——「DB 自体が目印」。
- **クラウド同期の危険は配置でなく警告で処理する。** 保存フォルダ全体がすでに `save-folder-guard.ts`（#95/#101）でクラウド同期先の警告を持っており、DB 1ファイルだけ特別扱いする理由がなくなった。同ドメインの実プロダクトも同じ選択をしている（下記）。
- **バックアップの一般ファイル収集からは明示的に除外する**（`hologram.db`/`-wal`/`-shm`）——ライブ書き込み中の DB をファイル単位でコピーするのは不整合になるため、整合コピーは Online Backup API 経由の世代ストア（#233）だけが担う。
- **複数ライブラリの切り替え（#176）は「DB を閉じる → ポインタを差し替える → 新しい場所で DB を開く（無ければ作成、世代があれば復元）」の3手で表現できる**——DB が外にある間は「ポインタを差し替えるだけ」では済まず、per-library の状態をどこかへ退避する仕組みが別途要っていた。

## 標準の照合（一次ソース）

- **Zotero**: `zotero.sqlite` はデータディレクトリ直下＝添付ファイルと同じ入れ物（公式 `support/zotero_data`）
- **Calibre**: `metadata.db` はライブラリフォルダの最上位。クラウド同期フォルダ（Google Drive・Dropbox 等）は明示的に非推奨と案内している（公式 manual FAQ）——「DB を外へ出す」ではなく「同期させるな」という警告で処理する側
- **Obsidian**: vault 固有の設定は vault 内 `.obsidian/`。vault の一覧と端末側の全体設定だけが端末側（公式ヘルプ）——「一覧は端末・中身はライブラリ」という帰属の線引きの前例

## 影響

- `dbFile()`（`app/src/main/index.ts`）は `getSaveFolder()` 直下を指す。設定ディレクトリに残っていた既存インストールの `hologram.db` は起動時に一回だけ新しい場所へ移す（リリース前に撤去してよい移行コード）
- 保存先の移動（`relocateLibrary`）は「DB を閉じる → フォルダごとコピー → ポインタを反転 → DB を開き直す → 検証してから旧側を削除」の順に組み直した（開いたままファイル単位でコピーしていた旧実装は不整合になり得た）
- ライブラリの識別子（`store_state.libraryId`）は #233 のバックアップ宛先の身元照合と、#176 の「ライブラリごとの端末側設定（バックアップ先・整合性ステータス）」の両方が使う
- `#232`（設定ディレクトリの既定パス標準化）は #176 より後に入れる方が軽い＝config ディレクトリの移動がライブ DB（＋WAL/SHM）を運ばずに済む

## 却下した案

- **設定ディレクトリのまま、ライブラリ id で分ける**（`libraries/<id>/hologram.db` ＋フォルダ内に id マーカー）— ADR 0010 の条項をそのまま保てるが、ライブラリが自己完結しない（フォルダを別端末へ運ぶと中身が消えたように見える）。マーカーファイルは結局フォルダ内に要る。同じフォルダを2台で開くと黙って分岐する
- **1つの DB に `library_id` 列を持たせる**— 全クエリに絞りが必要になりクロスリークが事故になる。ライブラリの削除が巨大な `DELETE` になる。同ドメインの実プロダクトに前例がない
