# 0011. 取得したペイロードを原本として残し、正規化フィールドへの昇格だけを実需で絞る

- 状態: 採用（2026-07-28）
- 関連: [#292](https://github.com/apricot-cake/hologram/issues/292)・[#191](https://github.com/apricot-cake/hologram/issues/191) API スキーマの破損検知・[0010](0010-sqlite-as-the-metadata-truth-source.md) メタデータの正本を SQLite に置く

## 背景

機能の採否は「実需が見えてから足す」で判断してきた。表示・検索・ファセットのようなサーフェスにはこれで正しい＝作らなくても、必要になった日に作れば同じものが手に入る。

**取得だけはこの式が成り立たない。** 投稿は削除され、アカウントは消える。保存時に拾わなかったデータは、後から必要になっても取り戻せない。可逆な判断と不可逆な判断に同じ物差しを当てていたのが問題だった（実例＝[#180](https://github.com/apricot-cake/hologram/issues/180)＝応答に含まれていた情報を URL 以外捨てていた）。

一方で「拾えるものを全部フィールドにする」は成立しない。列・サイト別の抽出モジュール・マイグレーション・テストの維持コストが項目数に比例して増え、しかも増えた分の大半は誰も使わない。

## 決定

**取得の過程で手元に来た応答を、加工せずそのまま保存する層を1つ置く。** 正規化フィールドへの昇格は従来どおり実需で絞る。

- **置き場はデータベース**（`raw_payloads` テーブル・1取得1行・gzip した BLOB）。ファイルを増やさず、バックアップ・移行・トランザクションを [0010](0010-sqlite-as-the-metadata-truth-source.md) の一本化に相乗りさせる。原本は**投稿と同じトランザクション**で確定する＝投稿だけが着いて原本が欠けた状態を作らない
- **1投稿に複数行**が普通（投稿本体の endpoint と投稿者プロフィールの endpoint は別の取得）。`sha256` は圧縮前バイト列に対する値＝どう圧縮したかではなく本文そのものを指す
- **追記のみ**。同じ取得を二度書いても増えず（再適用は冪等）、後の書き込みが先の取得を消すこともない
- **既定は全部残す。** 追加のリクエストを要さない＝すでに手元にあるものは、使う当てが無くても残す
- **原本の定義**: API 経路は受信した本文をそのまま。DOM 経路は、サイト別の抽出モジュールが正規化フィールドへ落とす直前の中間表現（版番号つき）を原本とする。**現時点で DOM から正規化フィールドを作る経路は無い**（DOM は投稿の特定にだけ使い、フィールドは API から取る）ので、この規則は先に置くだけで実装対象を持たない
- **境界は「そのレコードのために届いたペイロード」**。Cookie・Authorization ヘッダ・リクエストヘッダ・画面全体の DOM は含めない
- **上限を超えても保存は失敗させない。** レコード単位の圧縮前上限を設け、超えた分は本文を持たない行（`omitted:oversize`）として、取得があった事実と同一性だけ残す
- **持ち出し**: 完全 ZIP は原本を既定で同梱し、マニフェストに形式とプライバシー注意を書く。画像のみの ZIP には含めない
- **見せる面は作らない。** 原本を読む UI（生 JSON ビューア等）はこの決定の対象外＝開示は表示層側の別判断

### 前例

「生を残し、ビューは後から導出する」はアーカイブツールの型で、独自の発想ではない。

- twarc は API 応答の生 JSONL をそのまま成果物として保存する（生データが正・派生は後段）
- gallery-dl は `--write-info-json` / `--write-metadata` で取得メタデータを丸ごと書き出す
- ウェブアーカイブの WARC は HTTP 応答の生保存が形式の根幹

## 影響

- **後から遡れる。** 「ライブラリの言語構成を集計したい」のような要求が生まれたとき、過去の保存分（**すでに削除された投稿を含む**）へ遡って項目を作れる。#180 型の取りこぼしは構造的に起きなくなる
- **解釈できなくなった応答も残る。** 本文は解析の前に積むので、プラットフォームが形式を変えて解析に失敗した保存でも中身は手元に残る。#191（API スキーマ破損の検知）はカナリアとして維持するが、「読んでいないフィールドが消えた」の報告は原本から後日作れるため、あちらの完了条件からは外す
- **原本は正規化レコードより多くの第三者の断片を含む。** 応答をそのまま持つ以上、引用元・返信先・プロフィールなど、ライブラリの表示には出ない他者の情報が入りうる。ローカル保存・サーバー送信なしの前提は変わらないが、**ZIP を人に渡す時だけはライブラリの見た目より多くを渡すことになる**ので、マニフェストにその旨を書く
- **容量は実質増えない。** 応答は圧縮して数 KB で、同じレコードが持つメディア原寸（数百 KB〜数 MB）に対して誤差の範囲

## 却下した案

- **サイドカーの隣に `.raw.json.gz` を置く（ファイル案）** — ライブラリのフォルダに別のファイル群が増え、バックアップ・移行・整合の面倒が[0010](0010-sqlite-as-the-metadata-truth-source.md) と二重になる。投稿ごと JSON を撤去した直後に、撤去したばかりの経路を部分的に戻すことにもなる
- **拾えるものを全部フィールドへ昇格する** — 維持コストが項目数に比例して増え、その大半は使われない。原本層はこの二択（全部フィールドにするか捨てるか）自体を解消するために置く
- **重複排除と再圧縮** — 応答どうしは似ているので理屈の上では効くが、KB 級の節約のために「どの原本がどの原本を参照しているか」という状態を持つことになる。効く場面が見えてから考える
- **取得した本文を一度解析してから書き戻す形で持つ** — 書き戻した時点で「受け取ったもの」ではなくなる（解析に失敗した応答は保存できず、順序や表記の揺れも失われる）。原本層の存在意義そのものを損なう
