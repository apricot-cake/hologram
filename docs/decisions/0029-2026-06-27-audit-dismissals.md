# 0029. 2026-06-27 の監査で棄却した所見を repo に記録する（再調査ガード）

- 状態: 採用（2026-08-08）
- 関連: 残った調査項目＝#63〜#66／受容リスクの本体＝#63（SSRF ガードの DNS リバインディング）

## 背景

2026-06-27 に3面監査（セキュリティ／正しさ／パフォーマンス）を実施した。**残った調査項目は #63〜#66 として起票されたが、「調べた結果、通らないと判断した＝再調査しない」と決めた分だけ repo のどこにも記録が無かった**（タスクではないので Issue にせず、エージェント側の私的メモに置かれていた）。

その置き方は失敗だった。棄却の根拠は「この実装がこうなっているから通らない」という形で**コードに依存している**のに、コードから離れた場所に置いたため、実装が変わっても記録が変わらない。2026-08-08 に実際にそれが露見した（下の「影響」）。**根拠がコードにあるなら、記録もコードと同じ場所に置く。**

## 決定

- **セキュリティ側の棄却12項目を、根拠つきでこの ADR に記録する。** 以下は再調査しない。
  - **zip-slip**: 展開先の二重ガード。
  - **captureId のパストラバーサル**: `SAFE_ID` による形式検査を通ったものしか受けない。
  - **プロトタイプ汚染**: 取り込むのは own プロパティのみ。
  - **trash の未エスケープ `<img>`**: 制限的 CSP により script は発火しない。
  - **Referer 注入**: undici が CRLF を含むヘッダ値を拒否する。
  - **native message の長さ**: `allowed_origins` による発信元制限と ~1MB のフレーム上限。
  - **`onMessage` の sender 未検証**: `externally_connectable` を持たないため、拡張外から到達する経路が無い。
  - **install / restart スクリプト**: 固定パス・非昇格で動く。
  - **サイドカーのパス**: 常に basename を取り直し、フォルダ内に収まることを検査する。
  - **`shell.openExternal`**: `https?://` の allowlist。
  - **サプライチェーン**: 実行時の npm 依存ゼロ・lockfile でピン。
  - **`sandbox: true` の未設定**: Electron 20+ の既定が true で、`nodeIntegration: false` と併せて冗長。
- **受容したリスクはここに書かない**＝SSRF ガードの DNS リバインディングは「意図的に受け入れている未決」なので #63 が持ち続ける。この ADR が扱うのは「通らないと結論した」ものだけ。
- **根拠はモジュール名・識別子で書き、`file:line` を書かない**（行番号は即座に腐り、腐ったことが誰にも見えない）。

## 影響

- ⚠️**根拠にした実装が消えたら、その項目の棄却は無効になる。** 棄却は「安全である」という永続的な主張ではなく、「その時点のこの実装なら通らない」という条件付きの結論にすぎない。**この ADR の項目を引用する前に、根拠として挙げた識別子が今もコードにあることを確かめること。**
- **正しさ／データ整合性側の棄却11項目は、この ADR に引き継がない（破棄した）。** それらは共通して「サイドカーを原子的に書いている」ことを前提にしていたが、[ADR 0010](0010-sqlite-as-the-metadata-truth-source.md) でメタデータの真実源が SQLite へ移り、原子書きも `app/src/main/lib-atomic.ts` の汎用実装へ置き換わった。**旧アーキテクチャに対する棄却なので、そのまま持ち込むと「確かめてある」という誤った印象だけが残る。** DB 時代の整合性は改めて監査する対象で、この ADR は何も保証しない。
- 主要なハードニング（制限的 CSP／`contextIsolation` + `sandbox`／SSRF ガード／各種 allowlist・マジックバイト検査・zip-slip の二重ガード）は導入済みで、**実体はコードが真実源**。この ADR はそれを再説明しない。

## 却下した案

- **エージェント側のメモリに置き続ける**: 却下。コード依存の記録を repo の外へ置くと、実装が変わっても記録が追随せず、しかも**追随していないことが誰にも見えない**。実際に前提の識別子が消えたまま「棄却済み」として残っていた。
- **12件を個別に Issue 化して `not planned` で閉じる**: 却下。監査クリアの記録はタスクではないので、板に12件のノイズを増やすだけになる。まとまった判断は1つの決定として1ファイルに置く方が読める。
- **棄却をテストとして書き直す**: 一部は妥当（「zip-slip は通らない」等は実行可能な主張にできる）が、この ADR ではやらない。テストにするかどうかは各項目の性質の問題で、**まず記録の家を repo 内へ移すことを先に片付ける**。テスト化は必要になった項目から個別に行う。
